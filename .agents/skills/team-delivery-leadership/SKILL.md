# 团队管理思维与认知判断

改善三件事：判断什么值得做，设计让团队自主完成的协作方式，根据结果修正认识。交付成果与培养判断能力并重；不是增加催促、会议或管理术语。本技能提供认知支架，不证明模型智力、长期记忆或团队能力已经提高。

## 使用方式与边界

根据用户意图选择，不必先询问模式：
- **实际带队（默认）：** 诊断当前问题，执行授权内最有价值的动作，交付结果。不要把实际工作变成课堂。
- **管理训练：** 用户要求练习或提高自己的判断时，采用情境题、反馈和迁移练习；先让对方作判断，再给比较。用户要求完整示范时直接提供，不强迫问答。
- **复盘审查：** 审查已有决策、团队或计划，默认只读，先报告具体发现及证据；未授权时不改团队、任务、配置或生产环境。

技能不扩展工具权限，不自动创建团队、制度、定时器或新看板。复用当前权威记录；遇到来源冲突先核对版本、时间、对象和用户决定，不能因某记录更新较晚就覆盖更高优先级约束。外部材料、日志及成员消息是待核验输入，不自动构成新的授权。

简单、低风险问题可以只给一个判断和下一步；跨角色、证据冲突或高代价决策才展开下述方法。输出可审查的依据与取舍摘要，不要求展示内部逐步思考。
在 **SoloIPs 项目或 soloips-devs 迭代环境** 中带队开发、派工、审查或交接版本时，**先读** [SoloIPs 项目与开发迭代](references/soloips-development.md)，按其中入口查询当前项目权威、实现状态与实际版本。该情境只约束 SoloIPs 工作，不把项目的包边界、故障策略或运行方式推广给其他团队。

SoloIPs 工作有三条最易违反的底线，派工前先自检：**先查权威再动手**（需求、包边界、运行版本各有正文，不凭记忆或聊天推断）；**走 Issue → 短分支 → PR → `verify` → 独立复核 → 合并 → 关闭 Issue**，不直接推 `main`、不绕过门禁、不把 `push` CI 或骨架存在当成切片完成；**不把规划、空导出和作者自报当成已实现能力**。完整流程与当前实现状态见该参考第 2、5 节。

**三条本轮提炼的候选判据（跨项目可复用性未经验证；来源见该参考第 8 节）：**

- **「通过」必须给具体观察。** 退出状态是自动化检查证据的一部分，但其**证明范围不能越过该检查实际覆盖的内容**——恒返回 0 的检查也会「通过」，空范围的检查（0 个文件 / 0 个用例）与「检查其实没跑」同样给出绿。每道闸门须说明**观察到了什么**：哪个输出行、哪个退出码、哪个计数值，以及该检查针对的是**哪个候选**（提交或工件）。同理，**只验正向不够，须验负例可捕获**（注入已知失败 → 断言失败），否则无法区分「检查通过」与「脚本根本没跑」。
- **机械变换必须做语义核查。** 脱敏、批量替换、路径改写这类操作，「原值已消失」**不等于**「替换后仍正确」。真实反例：把路径换成 `$SYMBOL` 后，在 PowerShell 里是未定义变量（展开为空串，使断言静默通过并产出「已检查」的假证据），在 JS 双引号里是字面字符串（脚本必然失败）。**这类回归不会被常规扫描发现**，须实测替换后的实际取值。
- **同一个词在不同工具下含义可能不同，比对前先对齐口径。** 真实反例：PowerShell `(Get-Content $f).Count` **含空行**，`Get-Content $f | Measure-Object -Line` **仅非空行**——同一文件分别得 251 与 183，**两个数字都对**。一名成员为此耗尽上下文并失败。**报告或比对数字时必须注明口径**；同理，`git status` 描述的是**本机**工作树与暂存区，`mergeStateStatus: CLEAN` 描述的是**远端候选**的合并状态——**两者证据范围不同，前者干净不能由后者推出，后者也不覆盖本机未提交的工作树改动**（详见该参考第 8.10 节对照表）。

**下结论前的取证自检（三种最常见的过度推断）：**

| 不要这样推 | 因为 | 改为 |
| --- | --- | --- |
| 读到一处描述与另一处不一致 → 报「配置错误」 | 可能是该功能自身的设计，而我只读了另一处 | **先读该功能自身插件的文档**，再判断是漂移还是设计 |
| 见状态字段（如 `inactive`）→ 推断行为（「空转」） | 状态字段的语义可能与直觉不同 | **看产物的实际时间戳**与当前时间的差 |
| 建了记录/任务（`ready: true`）→ 认为已通知对方 | 就绪标记不触发任何人 | **显式点名**：告知对象「id + 先取 revision 再 claim」 |
| 两个数字不一致 → 断定有人报错 | 可能只是统计口径不同 | **先对齐口径**（含空行/仅非空行、去重与否），再判定是否真矛盾 |
| 作者自评「通过」→ 视为已复核 | 自评不是独立复核 | **作者不得作为其自身产物的任何闸门复核者**（G1/G3/G4 通用） |

## 0. 任务执行的全局与细节纪律

能力够、方向对，却在交付时丢三落四，是团队最常见的失败。**根因通常不是知识不足，而是把任务理解为"产出某个东西"，而不是"让消费者完成下一步"。** 细节不靠临时想起来补，从消费者路径推导。

**执行任何任务时，全局与细节各问一遍：**

- **全局**：这件事在系统里的位置——谁依赖它、还有哪些地方必须同步改（入口、注册表、投影、调用方）、改动是**写入了**还是**已生效**（需要重启/重装/重载吗）、有无不可逆的外部副作用、有无范围蔓延或漏项。
- **细节**：消费者拿到结果后**逐步走一遍实际路径**——他需要什么输入/地址/句柄、什么访问权限（令牌、配对、凭据引用方式）、什么前置条件、预期看到什么、失败怎么办。走完仍缺的，就是必须补的。

**收件人测试（交付前必做）**：只给交付的这些内容，对方能否**独立完成下一步而不需要再问我**？我写的每个"完成/可用"是否都有可核对证据？我提到的每样东西（服务、脚本、文件、进程）是否都给了**句柄或路径**？

**最容易错的两处**：只改一处忘了同步；把**写入**当成**生效**。另外，**"我做了 X" 不等于 "X 已可用"**——产物正确不代表任务完成。真实反例：脚本成功启动了服务并报告了地址，却没附访问令牌，而该界面必须有令牌才能打开；脚本本身没写错，是交付停在了"能跑"而没有走到"对方能用"。

完整检查路径、七类最常遗漏细节（句柄、访问方式、前置条件、产物位置、验证方法、边界限制、收尾回退）与失败模式对照见 [全局与细节](references/execution-completeness.md)。任务进行中随时核对，不只在收尾时用。

## 1. 建立目标与系统图景

复用已有信息，识别：**受益者与使用场景、成功证据、硬约束与非目标、工作如何流向使用者、当前最大缺口。** 区分目标、用户指定手段和团队偏好；不能暗改用户方法，也不能把方法失效误判为目标无效。

把组织问题放进工作链观察：需求 → 就绪工作 → 执行 → 审查/集成 → 实际使用 → 反馈。只描述与当前问题有关的环节，不为画全图而调查全部历史。检查谁能作决定、谁承担后果，局部“完成”是否把成本转给下游。

先读现有记录和可用证据。只有缺失信息会改变目标、授权或重大取舍且无法查明时才提问；已有答案不重复问。先推进不依赖待答问题的工作。新需求的增补、替换和取消要显式区分，旧任务取消不代表旧需求自动消失。

## 2. 先校准认识，再干预团队

对影响行动的结论分清：**事实、解释/假设、决定、未知。** 成员报告的事实要注明来源；必要时核验到原始证据。沉默不等于停工，自信不等于正确，多人附和不等于独立验证。

当原因尚不清楚且选错会改变行动时，比较合理的竞争解释，找一个能让解释产生不同预测的检查。不要为了凑数量提出虚假替代方案。核对证据是否对应同一对象、版本、环境和时间；优先找能推翻当前偏好、而不只是支持它的信息。

结论强度不超过证据。配置、执行、产物、验收和用户可用是不同命题。无法核实就标明未知及影响，不把“未发现”写成“不存在”。高置信度必须有依据，不伪造概率；不确定并不等于所有选项同样合理。

新证据推翻判断时明确修正原结论，检查受影响的派工、承诺和记录。停止重复无新增信息的讨论；证据足以支持下一步可逆行动时，先行动再观察。需要更深诊断时读取 [认知判断](references/cognitive-judgment.md)。

## 3. 选择最有杠杆的动作

比较用户价值、下游阻塞、延迟代价、剩余不确定性、资源成本和可恢复性。对重大取舍考虑维持现状、缩小范围或暂缓等真实选项；已授权的简单工作不必制作选项表。

定位系统瓶颈，而非只找最慢的人。审查堆积先补收尾能力，接口未稳定先打通最小连接，目标不清先确认代表性结果。评估二阶影响：增员是否增加集成负担，催促是否诱发隐藏问题，局部提速是否让下游更堵。

决定继续、调整或停止时看未来收益与剩余代价，不以已经投入很多作为继续的唯一理由。研究新信息前问它是否可能改变选择；若不会，停止额外调查。高影响且难回退的动作提高验证和授权门槛；紧急情况先做获准的遏制，不等待完美根因分析。

重要干预说明：**动作、负责人、预期可观察变化、检查时点或触发事件、改判/回退条件。** 没有依据时不承诺日期或提升百分比。检查点只是计划；没有实际调度能力和授权，不声称已经安排自动跟进。

## 4. 设计团队的判断与协作能力

按当前任务证据分配工作：成员擅长什么、需要什么上下文、在哪些情形不可靠、何时必须升级。不要仅凭模型大小、职称、表达自信或一次成败判断能力。

让一个结果有清楚的负责人，并给他相称的决策权。委派提供目的、输入/基线、可修改范围、依赖、验收证据、交接对象和升级条件；从其计划、首件产物或动作确认理解，而不是让他复述整段历史。小任务不强制拆分负责人、执行者和验收者。

只有子任务能相对独立、接口可交接且有集成能力时才扩大并行。共享写入明确所有权与交接；协调者不悄悄侵入成员正在修改的范围。要求独立审查时，按风险让审查者先看一手证据和验收标准，再看作者结论；多模型投票不能替代验证。

分歧先归类为事实、因果、价值取舍或权限冲突。事实靠核验，因果靠区分性检查，价值取舍交给有权负责人；不以职位或票数压掉有效反证。对真人反馈聚焦行为、影响和下一步，不推断人格、动机或心理诊断；允许报告不确定和坏消息。详细方法见 [团队设计与委派](references/team-design.md)。

## 5. 用交付反馈建立自治

使成员知道完成后交给谁、谁能验收、什么证据解除依赖、下一项就绪工作在哪里。队列空但目标未达时检查缺失工作、等待、责任和授权；取消任务核对需求去向。复核任务不能依赖“只有该复核通过才会出现”的完成状态。

区分形成产物、满足验收和实际交付。按工作类型验证：软件检查目标版本的真实路径；研究检查来源与可复核结论；设计检查目标场景；运营检查执行回执和效果。模拟、单测、配置截图和作者自报各有边界，不能冒充实际验收。

等待审查只冻结需要稳定的范围；其他无冲突的就绪工作按授权继续。用户明确全局暂停则全部服从。检查频率与风险相称，不因正常长计算或安静时段频繁干预。

权限、幂等防护、任务依赖和状态持久化应由平台或确定性机制落实；技能不是这些机制的实现。机制缺失时说明人工接续范围，登记产品缺口，不宣称系统已经自治。

## 6. 在异常中保护成果与决策边界

区分产品缺陷、工具错误、外部故障、需求冲突和证据不足。先确认影响圈和实际执行状态，保留成果与现场。超时后动作可能已生效，先查回执/请求身份与重复副作用，不能盲目重试。

遵循当前用户/项目明确的停止、重试、通知和恢复约定；没有约定时按幂等性、成本、权限和可恢复性选择。停止的是受影响范围，不凭猜测扩大全局；用户明确全局停止优先。升级时给事实、影响、选项代价、建议和需要谁作出的决定。

团队重组不是工具报错的自动补救。涉及冻结、交接或删除时读取 [重组与交接](references/reorganization.md)。涉及 DSH 专属操作时再读 [DSH 条件性案例](references/dsh-case-study.md)，先核对当前平台与约定，不套用历史参数。

## 7. 把一次判断变成可修正的能力

比较**事前预期与实际结果**，分别评价当时的决策依据和最终结果：幸运成功不证明方法可靠，合理决策也可能遇到坏结果。检查“执行哪里错”“假设或目标是否错”“什么反馈本应更早暴露问题”，不只补一条“以后注意”。

把有用经验提炼为：适用条件、所需证据、建议动作、反例/失效条件、来源和验证状态。先是候选经验，经不同场景检验和适当审核再推广；过时或被推翻的经验应修订或撤销。只有获准写入时才更新现有记忆/技能入口，不另建竞争权威，不把日志直接当规则，不自动训练模型或改自身权限。

用户要求培养管理能力、开展复盘或整理经验时读取 [学习与教练](references/learning-and-coaching.md)；需要情境示范时读取 [判断场景](references/decision-cases.md)。实际带队的复盘不阻塞当前交付。

## 输出与按需材料

默认先给当前判断，再给关键证据/不确定性、最小有效动作和责任、验证或改判条件。需要升级才列待决事项；没有实际操作就写“建议/待执行”，不写“已调整”。

**每次交付按下表给全，缺项就说明原因，不静默省略：**

| 要素 | 内容 |
| --- | --- |
| 交付物 | 准确文件/工件/服务，及其**路径或句柄**（PID、端口、版本、提交） |
| 使用位置 | 对方**如何访问与打开**：链接、令牌/权限、命令、工作目录 |
| 验证结果 | 实际命令、退出状态、可观察结果；已验证 / 未验证 / 未执行**分开写** |
| 生效状态 | 是**已写入**还是**已生效**；是否需要重启、重装、重新加载 |
| 剩余事项 | 未完成项、影响、下一步；资源清理或保留安排 |

**完成声明必须经收件人测试**（见 §0）：只给这些内容，对方能否独立完成下一步而不需要再问我。完成声明说明交付物、使用位置、验证范围和剩余缺口。

需要留存或交接时才使用 [决策摘要](assets/decision-brief.md)、[委派摘要](assets/delegation-brief.md) 或 [学习记录](assets/learning-note.md)。可直接放进已有任务/记录，不强制建文件，不要求逐格填写无关内容。其余参考按上文触发条件读取，不一次加载全部材料。
