# 全局与细节：把任务做成闭环

解决一类反复出现的失败：能力够、方向对，但**交付时丢三落四**——说了"已启动"没给访问方式，给了脚本没给依赖，改了配置没说要不要重启，宣布"完成"但对方无法接着做。

根因通常不是知识不足，而是**把任务理解为"产出某个东西"，而不是"让消费者完成下一步"**。细节不是靠临时想起来补的，是从消费者的实际路径里推导出来的。本文件给出一条可重复执行的检查路径。

用于**执行已确定的任务**；原因不明或重大取舍时先用 [认知判断](cognitive-judgment.md)。

## 1. 先写交付契约，再动手（全局锚点）

开工前用三五行回答，不必建文档，可放在当前答复或任务里：

- **谁消费这个结果，他下一步要做什么？**
- **完成后他必须能独立做到什么？**（可观察，不是"理解了"）
- **边界**：包含什么，明确不包含什么？
- **什么证据证明完成？**

第 1 条是全部细节的来源。**消费者下一步的动作决定了哪些细节是必需的**——同一份产物，交给"要打开界面的人"和"要审计代码的人"，必需细节完全不同。

契约缺失时先补齐；确实无法确定且会改变做法时再问，不要用"我先做出来再说"跳过。

## 2. 从消费者路径推导细节，不要凭记忆罗列

把消费者拿到结果后的**实际步骤逐条走一遍**，每一步问四个问题：

| 每一步需要 | 缺了会怎样 |
| --- | --- |
| 输入是什么（地址、命令、文件、句柄） | 对方不知道从哪开始 |
| 需要什么访问权限或凭据 | 拿不到，卡在门口 |
| 前置条件是否满足（依赖、环境、工作目录） | 命令报错，或跑出错误结果 |
| 预期看到什么、失败时怎么办 | 无法判断成功，出事无从下手 |

**走完这条路径仍缺的东西，就是你要补的细节。**这比"仔细检查一遍"可执行，因为它有明确终点。

**实例（真实案例）。** 任务是"写脚本启动一个 DSH 实例"。脚本启动成功，报告了 `url = http://127.0.0.1:55201`，看起来完整。但走一遍消费者路径：

1. 消费者下一步 → 在浏览器打开开发界面；
2. 该界面**要求访问令牌**，只有裸地址会被拒绝；
3. 令牌由 DSH 在启动时生成并写入 **stdout 日志**，而启动脚本的返回对象里只有 `url`，**没有令牌**；
4. 结论：交付不完整。**正确的交付是带令牌的完整链接，并说明令牌随重启变化、如何取得新链接。**

注意这里的失败点：**不是脚本写错了**，脚本工作正常；是交付者停在"脚本能跑"，没有走到"对方能用"。产物正确 ≠ 任务完成。

## 3. 七类最常遗漏的细节

按消费者路径推导后，再用这张表兜底核对。每类都问："我说了这件事，**句柄/入口给了吗**？"

| 类别 | 缺了会怎样 | 典型表现 |
| --- | --- | --- |
| **句柄与身份** | 对方无法定位或复现 | 说"启动了"不给 PID/端口/版本/提交 |
| **访问方式** | 卡在鉴权，或误用 | 给链接不给令牌；给命令不说权限 |
| **前置条件** | 命令直接失败 | 不说要先装依赖、设环境变量、切工作目录 |
| **产物位置** | 找不到结果 | 说"已生成"不给路径；说"已修复"不说改了什么 |
| **验证方法** | 无法判断真假 | 只给命令不给预期输出与退出码 |
| **边界与限制** | 把未知当已知，误导后续 | 未验证项被写成已验证；不适用范围没说 |
| **收尾与回退** | 资源泄漏或无法恢复 | 启动了不说怎么停；改动了不说怎么退 |

**"报告完成"必须带证据**：改动内容、验证命令、实际结果、未做项。没有证据的"已完成"不构成交付。

## 4. 交付前自检：收件人测试

发出前逐条问自己，任何一条答"不能"就回去补：

- **只给我交付的这些东西，对方能否独立完成下一步，而不需要再问我任何问题？**
- 我写的每个"完成/成功/可用"，**是否都有可核对的证据**？
- 我提到的每样东西（服务、脚本、文件、进程、配置），**是否都给了句柄或路径**？
- 我是否把 **"我做了 X" 写成了 "X 已可用"**？两者不同。
- 需要访问的东西，**访问方式给全了吗**（令牌、权限、配对、凭据引用方式）？
- 我是否**只验证了中间步骤**（能启动、能编译），却没有验证**最终目标**（对方能用）？

**收件人测试是判断"细节够不够"的唯一标准**，不是"我觉得说清楚了"。

## 5. 全局考虑：影响面与边界

细节之外，还要检查这件事**在系统里的位置**：

| 维度 | 要问的问题 |
| --- | --- |
| 上下游 | 谁依赖这个结果？谁会因为这个改动受影响？ |
| 一致性 | 还有哪些地方必须同步改？（入口、注册表、投影、文档、调用方） |
| 生效条件 | 改动**写入了**，还是**已经生效**？需要重启、重装、重新登录、重新加载吗？ |
| 反例与失败 | 最可能怎么坏？早期信号是什么？ |
| 不可逆性 | 有没有外部副作用（发送、发布、删除、付费）无法撤销？ |
| 范围蔓延 | 我是否顺手改了契约外的东西？或漏了契约内的东西？ |

**最容易错的两处**：一是**只改一处忘了同步**（改了正文没改入口/注册表/投影）；二是**混淆"写入"与"生效"**（改了配置就以为已生效，实际需要重启）。这两类都要在交付时明确写出。

## 6. 失败模式对照

| 表现 | 真实原因 | 纠正动作 |
| --- | --- | --- |
| 报告"已完成"，对方却不能用 | 在**产物层**宣布完成，没走到消费层 | 做收件人测试 |
| 给了操作没给结果 | 把**动作**当成交付 | 附退出码、实际输出、可观察变化 |
| 细节时有时无 | 靠临时想起来补 | 用 §2 路径推导 + §3 清单 |
| 改了 A 忘了 B | 没有查投影/一致性 | 用 §5 一致性列 |
| 配置改了但没生效 | 混淆写入与生效 | 明确写出是否需要重启/重载 |
| 把未验证说成已验证 | 证据分层不清 | 分开写"已验证 / 未验证 / 未执行" |
| 交付物散落各处 | 没有交付位置说明 | 给路径、给入口、给下一步 |

## 7. 与技能其它部分的关系

- **本节处理"已确定任务的完整性"**；原因不明、证据冲突或重大取舍时用 [认知判断](cognitive-judgment.md)。
- 与 SKILL §5 一致：**形成产物、满足验收、实际交付是三件事**；本文件是把"实际交付"变成可执行的检查。
- 委派他人时，同样的要求写进 [委派摘要](../assets/delegation-brief.md)：**交接对象、格式和位置**必须可执行。
- 在 SoloIPs 等具体项目中，路径、端口、令牌获取方式等**动态值不写进本文件**，按项目环境交接规程实时读取。
