## 1. 团队在开发什么

SoloIPs 面向 AI 原创 IP 的孵化、生产与发行。首版先完成内部生产闭环，以短剧 IP 简纲和第一支可播放 PV 为代表成果：目标明确、合法员工协作、素材和作品按版本保存、非作者审查、用户接受或退回，再接续授权内工作。具体范围与需求来源读 [产品架构](../../../../docs/architecture.md) SOLO-01–03、SOLO-A01–03 和首版章节；**不能把研发环境装好算成这个产品已经交付**。

要区分两个团队：**建设 SoloIPs 的研发团队**是研发手段；**SoloIPs 里的 AI 公司**是用户使用的产品能力。本参考只约束前者。研发队能写代码，不等于 AI 公司产品已可用；员工和任务很多，也不等于创作目标达成。

[技术架构 ARCH-D02](../../../../docs/technical-architecture.md)规划五个包职责，S0 交付四包，`tools-pv` 随 S1 在有真实制作工具时加入。

| 包职责 | 派工边界 |
| --- | --- |
| `bundle` | 装配声明与组合验证，不持有业务状态，无运行时 `src/index.ts` |
| `adapter-dsh` | 收敛全部 `@deepseek-ai/*` 依赖，向 core 暴露内部接口；不另建业务权威 |
| `core` | 公司身份、准入、作品、业务审核等业务事实的唯一写入口 |
| `web` | Host 桥与独立 Client；消费只读投影、提交命令意图，零可写业务状态 |
| `tools-pv` | 制作工具和外部 job 接入，经业务接口保存结果与准确版本；S1 才创建 |

协作链路是 **SoloIPs 公司与业务规则 → 官方 Agent Team → 官方 subagent → DSH Session 与模型执行**。官方 Team 持有原生 roster、任务与消息事实，core 持有业务事实和绑定；**原生任务 completed 不等于作品被用户接受**。所需扩展在 DSH 定制 fork 中实现并回归，SoloIPs 锁定定制工件。旧 `dsh-agent-swarm` 只作差异实现和测试经验参考，不装回第二套执行链。状态归属与尚需验证的门禁统一读 [SOLO-TEAM-01–11](../../../../docs/decisions/official-team-and-dsh-fork.md)。

## 2. 当前实现状态（派工前必须核对的既有事实）

团队最容易犯的错是把规划当成已完成能力，或把已建好的骨架当成已实现业务。截至本次核实：

| 层 | 实际状态 |
| --- | --- |
| 文档与治理 | 产品、技术、代码规范、开发迭代、环境交接、官方 fork 决定均已登记；注册表是文档身份正文 |
| 开发工具链 | **已建立并提交**：根 `package.json`、`pnpm-workspace.yaml`、`pnpm-lock.yaml`、`tsconfig.base.json`、`.editorconfig`、`.oxlintrc.json`、`vitest.config.ts`、Prettier 配置 |
| 包骨架 | `packages/{bundle,adapter-dsh,core,web}` 存在，`package.json.name` 为 `soloips-*`；`bundle` 只有 `cordis.patch.yml`（无 `src/index.ts`），其余三包源码仅 `export {}` 与占位注释，**无任何业务实现**；各包含一个契约测试 |
| 门禁 | `.github/workflows/verify.yml` 在 PR 与 `main` 推送时执行安装、格式、lint、typecheck、test、build |
| 运行实例 | soloips-devs 下已有可运行开发版本；具体版本、端口、插件与验证状态按 ENV-01 本机记录读取 |

**因此：环境与工具链已就绪，业务能力仍为零。** 派工前核对 `packages/`、公开导出、`release.json` 与已通过验收，不把规划、空导出或骨架占位当成可用能力；也不因为骨架已存在就认为某个业务切片已经完成。**本参考只陈述现状，不构成实施授权**——具体切片能否开工，按当前用户指令、项目绑定与 ARCH-D07 判断（技术收敛不等于实施许可）。

**已知不一致（须报告，不要猜）：** [代码规范 DEV-03 §2.1/§2.2](../../../../docs/governance/code-development-standard.md)的目录列写作 `packages/soloips-bundle/` 等，而磁盘实际目录是不带前缀的 `packages/bundle/` 等（`package.json.name` 才是 `soloips-*`）。派工与新建文件以**仓库实际目录**为准；发现规范与磁盘不一致时按 DEV-13 报告，不擅自改名或按表格臆造路径。

## 4. 角色与写权

- **用户**决定产品目标和最终业务验收；队长可解决受委托范围内的工程选择，不能把团队一致意见写成用户确认。
- **主智能体/队长**维护授权范围、任务依赖与实际版本，分配有界工作、裁定证据冲突、接续下一项就绪工作；负责人的总结不能替代独立检查。
- **写者**只改约定范围，交付候选与实际检查结果；发现另一写者的改动或接口冲突时先协调。
- **复核者**核对准确候选及一手证据，指出具体行为与影响；**作者不能给自己的作品生成独立通过记录**。
- **集成者**串行管理共享暂存区和合并，复核已审查提交、必需检查及交付范围；角色可按规模合并，但需要的独立审查仍由另一执行者完成。

同一可写面只安排一个写者；有真实冲突风险才建隔离 worktree（`.worktrees/<task>/`，分支默认 `codex/<task>`）。**官方 Team 默认共享工作目录，`writeScopes` 只是提示，既不锁文件也不自动隔离 checkout**；通过工具参数写了目录还不够，要核对执行者的真实工作目录。

## 5. 日常开发流程（本仓库已生效的闭环）

本仓库已有可执行的 Git 门禁，开发按 DEV-15 走，不要绕过：

1. **工作意图进 Issue。** 队长可把用户已授权需求整理成 Issue（模板见 `.github/ISSUE_TEMPLATE/`）；登记不等于用户确认，新增业务建议仍标〔提案〕。Issue 承载验收条件与交付结论。
2. **从集成分支建短分支。** 默认 `codex/<task>`；有写冲突风险时用隔离 worktree。不在共享工作树并行暂存。
3. **提交前跑适用检查。** 命令是根 `package.json` 的 `format:check`、`lint`、`typecheck`、`test`、`build`；精确版本与命令以仓库配置为唯一正文，规范中的表格不是运行结果。允许按受影响包收窄，但不能用空脚本或跳过用例填充门禁。
4. **开 PR 并关联 Issue。** 使用仓库 PR 模板，列明来源 Issue、变更与 [DEV-13](../../../../docs/governance/code-development-standard.md) 证据（需求与前后行为、改动范围、工件标识、实际命令与退出状态、剩余限制）。
5. **CI 必须通过。** `verify` 在 PR 事件上运行；`push` CI 通过**不**证明 PR 流程通过。
6. **独立复核先于合并。** 评审者审查准确提交；新提交出现后复核受影响结论。单账号协作允许 GitHub 必需批准数为 0，但仍须保留合并前独立复核记录，且**不得把它冒充成独立 GitHub 账号批准**。
7. **经 PR 合并，不直接推 `main`。** 分支保护要求必须 PR、通过 `verify`、保持最新基线、管理员受约束，禁止强推与删除；不使用管理员绕过。
8. **满足全部验收后关闭 Issue。** 部分交付用 `Related #NN` 保持未完成；验收需合并后验证时，先合并验证再记录结果关闭。

DSH 承接时，成员通过原生分配/领取入口执行，Task 引用 Issue URL，Issue 记录真实 Team/Task 标识；自动桥接未配置时由队长维护关联。**用户交由当前会话直接完成的有界工作，记录真实执行者与证据并说明未使用 DSH Task——不得补造 Task ID，也不得说成 DSH 集成验收。**

## 6. 用一版开发下一版

目录概念保持分离：`SOLOIPS_ROOT` 是产品源码，`DSH_FORK_CHECKOUT` 是定制底座源码，`SOLOIPS_DEVS_ROOT/versions/<version>` 是固定工件和独立运行数据。精确值从 ENV-02 本机记录取得；版本入口与工作目录读该版 `release.json`，不把源码目录当作运行安装目录。

按 DEVENV 执行以下约束，详细命令和插件组合直接读取其正文：

- 每个版本使用自己的 home、agents、端口及数据根；Profile 可同名 `soloips`，显式使用 `patchReload: startup`。负责开发的版本运行固定 tgz，下一版在新目录构建和验证，**不原地升级已冻结实例**，不使用界面 `update --latest`。
- 新版本从模板继承配置。供应商 `settings.yaml` 放在每版 **home 根**；默认 preset 按[研发模板](../../../../profiles/development/README.md)设置。密钥只从用户已授权来源复制，不进入 Git、日志、派工上下文或回执；不复制正在写入的 Session、任务和旧执行状态。
- DSH 定制开发开工及每次 fork 更新、集成或发布前，按 SOLO-TEAM-11 实时 fetch 官方最新 `master`，记录完整 SHA，保留自有补丁并对齐验证。发布前上游又前移时补齐受影响检查，不能拿缓存引用或相同版本号作最新代码证明。
- 使用 [runtime.ps1](../../../../scripts/development/runtime.ps1) 的 `verify / start / status / stop` 入口，参数及执行方式查 DEVENV-03。核对获准版本与进程归属；该启动器不提供任意启动方式下的跨 Host fence。停止前结束在途工作，**Windows 终止进程不等于优雅排空**。
- 配置验证、Web/插件装配、官方 Team 与研发工具调用、同一工件的重启读回分别取证。无密钥 fixture 通过不代替真实供应商、社区插件外部功能或业务验收。
- 下一版经相应验收后交接开发职责，旧版数据保留。需要延续会话或业务状态时单独做一致检查点和兼容验证；**切 Profile 只改装配，回退旧版不能自动恢复新版新增成果**。

配置、Skill 和提示词为团队提供规则入口；自动派工、失权拒绝、停线、审核放行和恢复需要真实 Host 机制与验证。缺少机制时说明人工管理范围和产品缺口，不声称“主智能体已能保证自治”。

## 7. 故障与交接的判断底线

**真实上游 API 首错立即停线。** 按 DEV-07 / ORG-13 停止受影响后续动作并通知用户，保留身份、任务和成果；不得自动重试、换路由、归档、删除或批量取消。恢复须用户明确指令。核对 SDK、插件轮询与中间件的隐式重试；**关闭一个 retry 行不能证明全团队已停**。离线故障注入按 DEV-07 的测试边界执行，不以真实故障为借口自动反复探测。

**保护运行环境。** 凭据、服务配置和新服务启动须有覆盖该动作的用户明确授权；默认不执行。不开原生 Windows 终端或目录选择窗口，不把用户数据和会话用作临时测试材料。

**区分证据层次。** 安装/启用不等于实际调用；构建不等于产品验收；源码候选不等于目标安装版本；模拟、单测与作者自报各有边界。恢复、独占、实际工具调用和作品接受分别核实。

一次交接要让接手者找到：**目标及剩余需求、准确候选/工件与配置身份、命令和退出状态、各层验证边界、Issue/Task/PR 与审查入口、数据及资源归属、未完成事项和恢复/释放条件**。本机路径、端口、PID、哈希和动态阻塞写入 ENV 规定的记录及工作项，不固化为 Skill 默认值。任务完成不等于用户接受；遇到证据不齐，继续可独立完成的授权工作，并明确缺少哪一层。

## 8. 实现切片流程与闸门（本轮实战提炼）

本节是候选经验的固化，来源为 r002 批 1 的实测与多成员独立复核。**适用条件**：在 SoloIPs 仓库编写产品实现切片、设计实现流程或判断闸门。**不适用**：纯文档治理改动（按 DEV-15 走 PR 即可）。

### 8.1 架构前后对照（G1 闸门，强制）

开发任一功能前必须给出**实测的**前后架构对照，不得凭记忆或推断描述现状：

| 项 | 要求 |
| --- | --- |
| **前架构** | 改之前的模块/服务/数据/接口现状；**必须读实际文件并给 `file:line`**，禁止写「当前大概是……」。**须绑定 revision（commit SHA）**，否则并行时行号会漂移 |
| **后架构** | 目标状态，标注**新增 / 修改 / 删除** |
| **差异表** | 改什么 / 影响谁 / **爆炸半径** / 对同版其他功能的影响 |
| **爆炸半径** | 会碰坏哪些包、模块、验收场景。**列不出不得进入下一步** |
| **契约** | 接口签名 + 数据 schema + 失败边界 + **预留扩展点** |
| **滚动基线** | 本功能「后架构」成为下一功能的「前架构」；架构始终有实测基线 |

**前瞻必答（G1 强制）**：*本接口为后续哪个功能预留了什么？不预留，后续哪个功能必须返工本功能？* **答不出具体功能名，G1 不通过。**

**预留的边界**：预留必须有据，不能盲目预留（[产品架构 §6](../../../../docs/architecture.md) 要求「需要它们时应有业务量或功能证据」）。只为**已证明会碰**的接口预留。**过度设计与返工同样是失败。**

**C/D 冲突的裁决规则**：前瞻必答项**只需答出「功能名 + 该功能会碰哪个接口」**，不要求现在实现扩展点；预留形式可以是契约里的一条注释或一个可选字段，而非空实现。

### 8.2 四道闸门（每道须给具体观察，不得只写「通过」）

| 闸门 | 检查什么 | 放行 |
| --- | --- | --- |
| **G1 架构评审** | 前后架构是否**实测**、爆炸半径是否列全、契约是否完整、前瞻必答是否答出功能名 | **任一非作者成员**（规则原文是「非作者」，不是「必须是 QA」）；代码类→另一名开发，文档类→文档复核者 |
| **G2 门禁** | `format:check` / `lint` / `typecheck` / `test` / `build` | 自动，以退出码为准 |
| **G3 提交复核** | 收窄到三项**只属于它**的检查：① 准确提交与 G1 通过的契约**逐项一致**；② **失败用例确实先红过**；③ DEV-13 证据格式齐备 | 非作者 |
| **G4 真实验收** | SOLO-ACC 场景 | **版本级**执行，见 8.3 |

**闸门通过判据（通用）**：**不得用「退出码 0」或「CI 绿」作为任何闸门的通过判据。** 每道闸门通过须给出**具体观察**——dump 的哪一行、命令的哪个退出码、请求计数的哪个值。依据：技术架构 §11.1（SOLO-F06）与基线「进程退出码 0 不是组合正确证据」。

**独立性不可合并**：「独立」是不可合并的常量，「深度」是可调变量——L1 纯文档无命令块 / L2 含可执行命令、路径或哈希（**须语义实测 + 洁净检出重放**）/ L3 公开接口、持久化、写权、恢复、停线、装配（完整 SOLO-ACC）。**同一人执行 G1/G3/G4 时，其独立性弱于分派三人，须原文记录该限制。**

### 8.3 组合断言与 G4 分层

**四道闸门不覆盖装配正确性。** W0 实测证明 `build` 成功对组合正确性零证明力，且 0.1.6 下**组合坏了四道闸门全绿**（重复 entry id 静默覆盖、Loader 回滚已删除、失败半径收窄为仅 7 个必需 id）。**因此组合断言（`--dump-config` 生效树比对）必须作为独立检查项，不能靠 G2 代替。**

**G4 分层**：**G4-M 机制层**（已安装工件 + 任务自建临时根，**不需要产品实例**）现在即可执行；**G4-P 产品层**（业务出口）等实现授权与实例。**G4 按验收场景就绪度触发，不按功能触发**——多数 SOLO-ACC 场景是跨功能的（ACC-04 需公司/部门/员工/入职齐备，ACC-05 需公司+部门+员工+任务+作品版本齐备），硬要求每功能 G4 会导致**为凑验收而伪造前置数据**，比不做更糟。

### 8.4 门禁必须自证确实运行了

**只验正向通过不够——恒返回 0 的门禁也会「通过」。** 每个新增门禁交付时**必须附一条「注入已知失败 → 断言失败」的证据**。本轮真实教训：门禁脚本的入口守卫写错会让它静默通过，**与它要防的失败模式同构**。

**脱敏（或任何机械文本变换）必须做语义核查**：「路径已消失」**不等于**「替换后仍正确」。本轮真实缺陷：把路径换成 `$SYMBOL` 后，在 PowerShell 里是未定义变量（展开为空串 → 断言静默通过并给出「已检查」的假证据），在 JS 双引号里是字面字符串（脚本必然 ENOENT）。**这类回归不会被常规扫描发现**，须实测替换后的实际取值。

### 8.5 版本级接口预研

功能级循环只有向后看的滚动基线，**没有向前看**，会导致后一功能返工前一功能。版本开工前须有一次**版本级预研**：消费耦合簇分析 → 本版 2–3 功能**一起**设计接口 → 产出**版本接口蓝图**（含对后续功能的预留点）。

### 8.6 临时工（人手不足时）

**编制上限 8 人**（平台 `TEAM_MEMBER_LIMIT`），而 `workflow` 的一次性子智能体**不计入该上限**。

- **谁派**：**任务负责人自己派**，Lead 不代派。Lead 只做授权判定、创建/打断持久队员、对外汇报。
- **何时用**：一次性工作（基线核对、参考提取、文档校对、独立复核、索引汇总）且编制已满；或缺特定视角。
- **何时不用**：需要跨轮记忆与任务板归属的持久工作；需连续写产品代码的工作；同一可写面的连续修改（临时工每次是新实例）。
- **要求**：产出**必须留档汇总到任务交付目录**，不得只留在临时工会话里；证据标准不降级（`file:line`、三类标注、不用「大概」）；一次性的，用完即散。
- **多模型互查的唯一途径**：持久队员模型继承会话默认（`SpawnTeammateRequest` **无 `model` 字段**，已核实源码），要模型多样性必须走 `workflow` 的 `agent(prompt, {provider, model})`。

### 8.7 授权链与暂停

三段式：**用户批准需求 → 队长批准调度 → 协调者派工**。协调者是**调度者**：派工、盯进度、指挥、汇总、上报、把关闸门、维护 Issue/PR 关联；**不认领交付物**（不写文档、不写代码）。发现疑似越界立即上报，不自行放行。

**必须停下请示用户**：[项目入口 §2](../../../../AGENTS.md) 的 8 种暂停条件。队长保留创建/打断队员（平台限制 `TEAM_LEAD_REQUIRED`）与授权边界判定。

### 8.8 队长不进入等待状态

有协调者时，队长**不轮询、不 `wait_agent` 长时间阻塞**，保持随时应答用户；进度由协调者上报。**在途任务阻塞文件写入，但不阻塞思考**——设计、分析、共识征集可并行推进。

### 8.9 队长本人的六条失效模式（本轮真实发生，逐条有反例）

本节记录**队长实际犯过的错**，每条附当时的真实情形与纠正动作。**这些不是假设风险，是已发生的失效**；接手者应把它们当检查表用。

**① 未取证就上报异常。**
真实情形：r001 监听 `0.0.0.0:55201`，我读了实例的 `home/AGENTS.md`（写着「remote 仅本机监听」）就报为「配置漂移、待裁定」。**实际是 `dsh-remote-web-ui` 的既有功能**——插件文档明写它会写受管块把绑定固定为 `0.0.0.0`，且 `reconciliation/` 里有该功能的修复备份。
**纠正**：报告环境异常前，**先读该功能自身插件的文档**（`.artifacts/.../unpacked/<plugin>/` 或包内 README），再判断是漂移还是设计。**「与我读到的另一处描述不一致」不等于「配置错误」。**

**② 把「建任务」当成「派工」。**
真实情形：我用 `team_task_create` 建了 task-11/task-12，见 `ready: true` 就认为已派出。**实际两者长期无 owner**——`team_task_create` 建的是**无主任务**。
**纠正**：平台规则明确「**Task readiness never starts an owner**」。建任务后**必须立即点名**：`team_task_create` → 紧接着 `send_message` 通知具体成员「任务 id + 用 `team_task_get` 拿 revision 再 claim」。**`ready` 只是标记，不是通知。**

**③ 误读成员状态为「空转」。**
真实情形：`list_agents` 显示 6 人 `inactive`，我据此报「6 人空转，而任务无人做」。**实测推翻**——`inactive` 是「本轮 turn 已结束、在等新任务」，当时 `core-dev` 36 秒前刚写入文件。
**纠正**：判断是否空转**看交付物的 `LastWriteTime` 与当前时间的差**，不看 `inactive`。`inactive` + 无未完成任务 = 正常待命。

**④ 一次摊开过多功能。**
真实情形：我一次报「8 个功能一起开发」，用户纠正「一个版本 2–3 个功能够了」。
**纠正**：**每版 2–3 个功能**（见 8.5 版本级预研）。且先判「哪些是一起的、哪些能拆」（同 domain/同文件/接口是否冻结），**不按功能名数量派工**。

**⑤ 越界代做执行工作。**
真实情形：我两次越界——自己读文件跑命令写基线文档、自己用 `workflow` 派临时工做 task-10 索引。用户两次纠正。
**纠正**：队长的活是**授权判定、创建/打断队员、对外汇报、关键结论独立复核**。**写文件与派临时工都是任务负责人的事**（见 8.6）。**判断标准：如果我在写交付物，那就是错的。**

**⑥ 给用户的答复里混入工程编号。**
真实情形：我用 `T00`/`T03`/`fence`/`seam` 汇报，用户指出「我连 r002 需求都不清楚，你没给我说具体功能的名字和作用」。
**纠正**：对用户**用产品语言**说功能（「建公司」「招员工」「重启不丢」），工程编号只在团队内部使用。**用户视角的功能清单与内部任务编号要分开表述。**

**⑦ 用活动目标代替可验证目标。**
真实情形：我连续四轮把「等用户确认需求/授权」当阻塞项上报，用户纠正「**我肯定不能现在拍板。开发流程根本没有设计完成**」。根因是我把「task-11 完成流程设计」当成目标——**那是活动，不是结果**。
**纠正**：按 `define-goal` 的质量门槛自检——目标必须答出「什么会变成真的 / 什么证据证明它 / 什么量化或二元阈值定义成功 / 什么范围边界 / 什么情况停下来问」。**纯活动目标（「推进」「继续调查」「收齐材料」）必须先改写成可验证结果**。判断信号：**当我在反复催同一件事时，通常不是对方拖延，而是目标没定义。**

**⑧ 用「完成声明」代替证据链。**
真实情形：我在没有走查样例时就准备把流程标为「设计完成」；用户指出流程「根本没设计完成」。
**纠正**：区分「文档写完」与「流程能用」。**判据必须是「流程被执行过一次且产出可判定结果」**（如用模板对首个功能做完整走查、通过 G1 逐条判据），而非「文件存在」。见 8.1–8.5。

### 8.10 工具语义差异导致的两类假矛盾（本轮真实浪费）

**① 行数口径。** PowerShell 中 `(Get-Content $f).Count` **含空行**，`Get-Content $f | Measure-Object -Line` **仅非空行**。同一文件实测 251 vs 183（差 68 行空行）、253 vs 177、347 vs 240。
**真实后果**：一名成员为核对「183 vs 251」的差异**耗尽上下文并 failed**；协调者随后也一度用不同口径比对而得出混乱数字。**两个数字都对，没有任何人报错。**
**规则**：报告或比对数字时**注明口径**（含空行 / 仅非空行 / 去重与否）。**不同口径的数字不构成矛盾。**

**② 干净状态口径。** `git status` 干净、`mergeStateStatus: CLEAN`、`verify` CI 通过——**三者都只看已提交内容，均不覆盖未提交的工作树改动**。
**真实后果**：PR head 完好而工作树被覆盖掉 44 行，`mergeStateStatus` 仍为 `CLEAN`。若据此合并，**丢内容不会被任何自动检查发现**。
**规则**：**合并前须核对 `git status`**，不能只用 `mergeStateStatus: CLEAN` 作就绪判据。**这与「不得用退出码 0 作通过判据」同族。**

### 8.11 作者不得自审（R5，本轮补入）

**规则**：**作者不得作为其自身产物的任何闸门复核者**（G1/G3/G4 通用，不限于 G1）。

**来源与理由**：R3 只说「G1 分派任一非作者」，**未禁止「作者复核自己产物」**。本轮出现实例：`verifier` 同时是 `acceptance-plan.md` 的作者，若它做该文档的 G4 复核即构成自审，**与「作者不得自审」直接冲突**。

**另一条配套洞见（`integrator` 提出，已采纳）**：
> **流程的真实安全来自「多名智能体互相不同意」，不是来自闸门数量。** 本轮两项阻断回归都由**别人**抓出（B-1 由 `verifier` 发现而首轮复核者漏报；B-2 断链由 `doc-reviewer` 发现而执行者没测到）。**缩到 1 名复核者会断崖式下降，而 `requiredApprovingReviewCount: 0` 会让它看起来像已满足。**

### 8.12 候选经验必须标注验证状态

**规则**：把单场景、单项目的经验写进通用 Skill 时，**必须标注验证状态**，不得直接声明为「跨项目适用」。

**本轮实例**：第 8 节的经验来自 **r002 批 1 单场景检验**，却在 `SKILL.md` 中被写成「两条**跨项目适用**的判据」——**与同一文件既有的「不把项目的包边界、故障策略或运行方式推广给其他团队」直接冲突**，且跳过了该文件自己要求的「经不同场景检验和适当审核再推广」。

**纠正后的措辞**：标注为「**本轮提炼的候选判据（跨项目可复用性未经验证）**」；参考正文追加「**本节全部条目的验证状态为〔候选〕**：仅经 r002 批 1 单场景检验」。

**同族纪律**：**不要把未验证结论写成已验证**。正面例子——`doc-reviewer` 把「临时工不占编制」标为〔推断〕而非事实（源码路径支持，但本轮未实际派过），并写明首次派工须验证。**这个标注方式是对的。**


**共同根因**：①②③ 都是**没取证就下结论**——读了一处描述就推全局、见一个状态字段就推行为、用标记代替通知。**报告前先问：我的结论绑定了哪个实测证据？**
