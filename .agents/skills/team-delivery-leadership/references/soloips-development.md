## 1. 团队在开发什么

SoloIPs 面向 AI 原创 IP 的孵化、生产与发行。首版先完成内部生产闭环，以短剧 IP 简纲和第一支可播放 PV 为代表成果：目标明确、合法员工协作、素材和作品按版本保存、非作者审查、用户接受或退回，再接续授权内工作。具体范围与需求来源读 [产品架构](../../../../docs/architecture.md) SOLO-01–03、SOLO-A01–03 和首版章节；**不能把研发环境装好算成这个产品已经交付**。

要区分两个团队：**建设 SoloIPs 的研发团队**是研发手段；**SoloIPs 里的 AI 公司**是用户使用的产品能力。本参考只约束前者。研发队能写代码，不等于 AI 公司产品已可用；员工和任务很多，也不等于创作目标达成。

[技术架构 ARCH-D02](../../../../docs/technical-architecture.md)规划五个包职责，S0 交付四包，`tools-pv` 随 S1 在有真实制作工具时加入。

| 包职责 | 派工边界 |
| --- | --- |
| `bundle` | 装配声明与组合验证，不持有业务状态，无运行时 `src/index.ts` |
| `adapter-dsh` | 收敛全部 `@deepseek-ai/*` 依赖，向 core 暴露内部接口；不另建业务权威 |
| `core` | 公司身份、准入、作品、业务审核等业务事实的唯一写入口 |
| `web` | Host 桥与独立 Client；消费只读投影、提交命令意图，零可写业务状态 |
| `tools-pv` | 制作工具和外部 job 接入，经业务接口保存结果与准确版本；S1 才创建 |

协作链路是 **SoloIPs 公司与业务规则 → 官方 Agent Team → 官方 subagent → DSH Session 与模型执行**。官方 Team 持有原生 roster、任务与消息事实，core 持有业务事实和绑定；**原生任务 completed 不等于作品被用户接受**。所需扩展在 DSH 定制 fork 中实现并回归，SoloIPs 锁定定制工件。旧 `dsh-agent-swarm` 只作差异实现和测试经验参考，不装回第二套执行链。状态归属与尚需验证的门禁统一读 [SOLO-TEAM-01–11](../../../../docs/decisions/official-team-and-dsh-fork.md)。

## 2. 当前实现状态（派工前必须核对的既有事实）

团队最容易犯的错是把规划当成已完成能力，或把已建好的骨架当成已实现业务。截至本次核实：

| 层 | 实际状态 |
| --- | --- |
| 文档与治理 | 产品、技术、代码规范、开发迭代、环境交接、官方 fork 决定均已登记；注册表是文档身份正文 |
| 开发工具链 | **已建立并提交**：根 `package.json`、`pnpm-workspace.yaml`、`pnpm-lock.yaml`、`tsconfig.base.json`、`.editorconfig`、`.oxlintrc.json`、`vitest.config.ts`、Prettier 配置 |
| 包骨架 | `packages/{bundle,adapter-dsh,core,web}` 存在，`package.json.name` 为 `soloips-*`；`bundle` 只有 `cordis.patch.yml`（无 `src/index.ts`），其余三包源码仅 `export {}` 与占位注释，**无任何业务实现**；各包含一个契约测试 |
| 门禁 | `.github/workflows/verify.yml` 在 PR 与 `main` 推送时执行安装、格式、lint、typecheck、test、build |
| 运行实例 | soloips-devs 下已有可运行开发版本；具体版本、端口、插件与验证状态按 ENV-01 本机记录读取 |

**因此：环境与工具链已就绪，业务能力仍为零。** 派工前核对 `packages/`、公开导出、`release.json` 与已通过验收，不把规划、空导出或骨架占位当成可用能力；也不因为骨架已存在就认为某个业务切片已经完成。**本参考只陈述现状，不构成实施授权**——具体切片能否开工，按当前用户指令、项目绑定与 ARCH-D07 判断（技术收敛不等于实施许可）。

**已知不一致（须报告，不要猜）：** [代码规范 DEV-03 §2.1/§2.2](../../../../docs/governance/code-development-standard.md)的目录列写作 `packages/soloips-bundle/` 等，而磁盘实际目录是不带前缀的 `packages/bundle/` 等（`package.json.name` 才是 `soloips-*`）。派工与新建文件以**仓库实际目录**为准；发现规范与磁盘不一致时按 DEV-13 报告，不擅自改名或按表格臆造路径。

## 4. 角色与写权

- **用户**决定产品目标和最终业务验收；队长可解决受委托范围内的工程选择，不能把团队一致意见写成用户确认。
- **主智能体/队长**维护授权范围、任务依赖与实际版本，分配有界工作、裁定证据冲突、接续下一项就绪工作；负责人的总结不能替代独立检查。
- **写者**只改约定范围，交付候选与实际检查结果；发现另一写者的改动或接口冲突时先协调。
- **复核者**核对准确候选及一手证据，指出具体行为与影响；**作者不能给自己的作品生成独立通过记录**。
- **集成者**串行管理共享暂存区和合并，复核已审查提交、必需检查及交付范围；角色可按规模合并，但需要的独立审查仍由另一执行者完成。

同一可写面只安排一个写者；有真实冲突风险才建隔离 worktree（`.worktrees/<task>/`，分支默认 `codex/<task>`）。**官方 Team 默认共享工作目录，`writeScopes` 只是提示，既不锁文件也不自动隔离 checkout**；通过工具参数写了目录还不够，要核对执行者的真实工作目录。

## 5. 日常开发流程（本仓库已生效的闭环）

本仓库已有可执行的 Git 门禁，开发按 DEV-15 走，不要绕过：

1. **工作意图进 Issue。** 队长可把用户已授权需求整理成 Issue（模板见 `.github/ISSUE_TEMPLATE/`）；登记不等于用户确认，新增业务建议仍标〔提案〕。Issue 承载验收条件与交付结论。
2. **从集成分支建短分支。** 默认 `codex/<task>`；有写冲突风险时用隔离 worktree。不在共享工作树并行暂存。
3. **提交前跑适用检查。** 命令是根 `package.json` 的 `format:check`、`lint`、`typecheck`、`test`、`build`；精确版本与命令以仓库配置为唯一正文，规范中的表格不是运行结果。允许按受影响包收窄，但不能用空脚本或跳过用例填充门禁。
4. **开 PR 并关联 Issue。** 使用仓库 PR 模板，列明来源 Issue、变更与 [DEV-13](../../../../docs/governance/code-development-standard.md) 证据（需求与前后行为、改动范围、工件标识、实际命令与退出状态、剩余限制）。
5. **CI 必须通过。** `verify` 在 PR 事件上运行；`push` CI 通过**不**证明 PR 流程通过。
6. **独立复核先于合并。** 评审者审查准确提交；新提交出现后复核受影响结论。单账号协作允许 GitHub 必需批准数为 0，但仍须保留合并前独立复核记录，且**不得把它冒充成独立 GitHub 账号批准**。
7. **经 PR 合并，不直接推 `main`。** 分支保护要求必须 PR、通过 `verify`、保持最新基线、管理员受约束，禁止强推与删除；不使用管理员绕过。
8. **满足全部验收后关闭 Issue。** 部分交付用 `Related #NN` 保持未完成；验收需合并后验证时，先合并验证再记录结果关闭。

DSH 承接时，成员通过原生分配/领取入口执行，Task 引用 Issue URL，Issue 记录真实 Team/Task 标识；自动桥接未配置时由队长维护关联。**用户交由当前会话直接完成的有界工作，记录真实执行者与证据并说明未使用 DSH Task——不得补造 Task ID，也不得说成 DSH 集成验收。**

## 6. 用一版开发下一版

目录概念保持分离：`SOLOIPS_ROOT` 是产品源码，`DSH_FORK_CHECKOUT` 是定制底座源码，`SOLOIPS_DEVS_ROOT/versions/<version>` 是固定工件和独立运行数据。精确值从 ENV-02 本机记录取得；版本入口与工作目录读该版 `release.json`，不把源码目录当作运行安装目录。

按 DEVENV 执行以下约束，详细命令和插件组合直接读取其正文：

- 每个版本使用自己的 home、agents、端口及数据根；Profile 可同名 `soloips`，显式使用 `patchReload: startup`。负责开发的版本运行固定 tgz，下一版在新目录构建和验证，**不原地升级已冻结实例**，不使用界面 `update --latest`。
- 新版本从模板继承配置。供应商 `settings.yaml` 放在每版 **home 根**；默认 preset 按[研发模板](../../../../profiles/development/README.md)设置。密钥只从用户已授权来源复制，不进入 Git、日志、派工上下文或回执；不复制正在写入的 Session、任务和旧执行状态。
- DSH 定制开发开工及每次 fork 更新、集成或发布前，按 SOLO-TEAM-11 实时 fetch 官方最新 `master`，记录完整 SHA，保留自有补丁并对齐验证。发布前上游又前移时补齐受影响检查，不能拿缓存引用或相同版本号作最新代码证明。
- 使用 [runtime.ps1](../../../../scripts/development/runtime.ps1) 的 `verify / start / status / stop` 入口，参数及执行方式查 DEVENV-03。核对获准版本与进程归属；该启动器不提供任意启动方式下的跨 Host fence。停止前结束在途工作，**Windows 终止进程不等于优雅排空**。
- 配置验证、Web/插件装配、官方 Team 与研发工具调用、同一工件的重启读回分别取证。无密钥 fixture 通过不代替真实供应商、社区插件外部功能或业务验收。
- 下一版经相应验收后交接开发职责，旧版数据保留。需要延续会话或业务状态时单独做一致检查点和兼容验证；**切 Profile 只改装配，回退旧版不能自动恢复新版新增成果**。

配置、Skill 和提示词为团队提供规则入口；自动派工、失权拒绝、停线、审核放行和恢复需要真实 Host 机制与验证。缺少机制时说明人工管理范围和产品缺口，不声称“主智能体已能保证自治”。

## 7. 故障与交接的判断底线

**真实上游 API 首错立即停线。** 按 DEV-07 / ORG-13 停止受影响后续动作并通知用户，保留身份、任务和成果；不得自动重试、换路由、归档、删除或批量取消。恢复须用户明确指令。核对 SDK、插件轮询与中间件的隐式重试；**关闭一个 retry 行不能证明全团队已停**。离线故障注入按 DEV-07 的测试边界执行，不以真实故障为借口自动反复探测。

**保护运行环境。** 凭据、服务配置和新服务启动须有覆盖该动作的用户明确授权；默认不执行。不开原生 Windows 终端或目录选择窗口，不把用户数据和会话用作临时测试材料。

**区分证据层次。** 安装/启用不等于实际调用；构建不等于产品验收；源码候选不等于目标安装版本；模拟、单测与作者自报各有边界。恢复、独占、实际工具调用和作品接受分别核实。

一次交接要让接手者找到：**目标及剩余需求、准确候选/工件与配置身份、命令和退出状态、各层验证边界、Issue/Task/PR 与审查入口、数据及资源归属、未完成事项和恢复/释放条件**。本机路径、端口、PID、哈希和动态阻塞写入 ENV 规定的记录及工作项，不固化为 Skill 默认值。任务完成不等于用户接受；遇到证据不齐，继续可独立完成的授权工作，并明确缺少哪一层。
