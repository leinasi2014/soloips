## 1. 开发模式定义

### 1.1 核心原则

```
一个会话 = 一个任务 = 对应难度选择模型
```

| 角色 | 职责 | 模型选择 | 说明 |
|---|---|---|---|
| **主会话（指挥）** | 统筹协调、任务分解、派发、审查、集成、汇报 | **Fable 5.1** | 编码73.4%、科学推理52.6%、更便宜更快 |
| **子智能体** | 按角色执行具体任务（检索调查、代码实现、独立验收、文档维护） | 由指挥会话在派发时指定 | **经 ZCode Agent 工具派发**（当前通道，见 §4）；DSH 派发为未来阶段路线（§4.6） |

### 1.3 Fable 5.1 vs Opus 5 性能对比

| 基准测试 | Fable 5.1 | Opus 5 | 差距 |
|---------|-----------|--------|------|
| Terminal-Bench-Science (科学推理) | **52.6%** | 29.0% | +23.6% |
| CursorBench (代理编码) | **73.4%** | 70.0% | +3.4% |
| Humanity's Last Exam (多学科推理) | **65.0%** | 63.6% | +1.4% |
| Terminal-Bench 4.0 (终端编码) | **55.8%** | 42.0% | +13.8% |
| AutomationBench (业务流程) | **31.4%** | 26.9% | +4.5% |

**结论**：Fable 5.1 在开发相关任务上全面领先，价格更低、速度更快。Opus 5 仅在高安全级别场景保留。

### 1.4 思考强度配置

| 强度 | 使用场景 | 说明 |
|---|---|---|
| `high` | 系统设计、跨模块重构、新技术引入 | 深度推理（仅必要时） |
| `medium` | **默认**，包括架构设计、复杂决策、代码实现 | Fable 速度快，medium 性价比最高 |
| `low` | 简单确认、格式调整、文档整理 | 快速执行 |
| `off` | **禁止使用** | 不适用于开发场景 |
| `max` | **禁止使用** | 浪费资源 |

## 2. 任务难度分级

### 2.1 难度定义

| 等级 | 任务特征 | 指挥模型 | 思考强度 | 子 Agent 数量 |
|---|---|---|---|---|
| **L1 简单** | 文档整理、单文件修改、格式调整 | Fable | `low` | 1个 |
| **L2 标准** | 功能实现、单元测试、简单重构 | Fable | `medium` | 1-2个 |
| **L3 复杂** | 多包协调、API设计、性能优化 | **Fable** | `medium` | 2-3个 |
| **L4 架构** | 系统设计、跨模块重构、新技术引入 | **Fable** | `high` | 3+个 |

> **注意**：L3-L4 原本用 Opus，现在改用 Fable，因为 Fable 5.1 在编码任务上全面领先。Opus 仅在高安全场景保留。

### 2.2 难度判断标准

```
L1: 单文件改动 < 100行
L2: 单包改动，功能边界清晰，有明确验收标准
L3: 多包改动，涉及接口变更，需要协调
L4: 新系统/子系统设计，影响多个团队/模块
```

### 4.1 依据：实际运行经验（〔源码事实〕，2026-09-17）

> **来源**：2026-09-17 本机实际运行记录（指挥会话的运行记录 + 文档智能体首任/第三任的第一手参与经验）。**边界**：这是运行观察，不是设计稿，也不证明该体系已覆盖全部任务类型或已通过完整验收；它描述的是**当前实际在做的事**。

当日实际发生并验证的结构：

| 运行事实 | 观察内容 |
|---|---|
| **并行多线流水线** | Drizzle 存储重构以多条写线并行推进（不同包/文件面），指挥会话统一调度与终审 |
| **常驻文档智能体** | 文档审查·确认·更新智能体被派发两任（首任写 V1 UI 决策；第三任修订本文档），具备跨任连续性 |
| **写面白名单隔离** | 各写手子智能体的写范围被显式限定（如「只改 multi-agent-development.md」「不得触碰 AGENTS.md」），并行写手之间无撞车 |
| **独立验收与在途隔离** | 指挥会话保留在途改动不被覆盖；另一实例修订其他文档时，本文档不在其清单内，据此判定无冲突 |

### 4.2 指挥会话（主会话）

| 项 | 内容 |
|---|---|
| 角色 | 拆解、派发、审查、终审提交、汇报 |
| 运行位置 | ZCode 主会话 |
| 工具 | Read/Edit/Write/Bash/Agent/TodoWrite |
| 模型 | 主会话模型（见 §0.1；用户可随时调整） |

指挥会话是**唯一的终审与提交者**：子智能体的产出必须经指挥审查后才进入仓库（§4.4 第 4 条）。

### 4.3 子智能体角色与分工

子智能体**按角色后台并行**，而非按包拆分：

| 角色类型 | 职责 | 生命周期 |
|---|---|---|
| **检索调查型** | 代码搜索、事实核查、影响面调查 | **用后即弃**（一次性） |
| **代码写手** | 在指定写面内实现代码改动 | 按任务派发 |
| **QA 独立验收** | 独立复现与验证，**独立于写手** | 按任务派发 |
| **文档维护型** | 文档审查·确认·更新（含跨任连续性） | **领域型常驻复用** |

> **说明**：表中角色来自 2026-09-17 实际运行（§4.1）。「常驻」指同一领域智能体可被反复唤醒复用，不是常驻进程；其状态由文档与仓库承载（见 §4.1 文档智能体两任）。

### 4.4 关键纪律（〔约束〕）

以下为 2026-09-17 实际运行总结的工程约束，是本项目技术裁定：

1. **〔约束〕写面白名单隔离防并发冲突。** 每个写手子智能体必须获得显式写范围（允许改哪些文件/目录、明确不得触碰哪些文件）；范围外文件不得修改。理由：并行写手若共享文件面会互相覆盖，且无法归因。
2. **〔约束〕QA 独立于写手。** 验收由独立子智能体执行，不由实现该改动的写手自证。理由：证据分层红线——实现者自证不构成独立验收。
3. **〔约束〕领域型智能体常驻复用，调查型用后即弃。** 领域型（如文档智能体）保留连续性、可被反复唤醒；一次性调查用完即弃，不保留。
4. **〔约束〕子智能体一律禁 commit；由指挥终审后统一提交。** 子智能体不得执行 `commit` / `push`；改动经指挥审查后由指挥统一提交，保证提交粒度与信息一致、终审权唯一。

> **这些纪律不蕴含**：不声明所有任务都必须并行，不声明子智能体数量与任务规模成正比，不声明该体系已覆盖 UI/运行时类验收（真实浏览器等验证仍按 `docs/technical/acceptance.md`）。

### 4.5 工作区隔离与 Git 管理

**工作区隔离**：

| 层级 | 隔离方式 | 说明 |
|---|---|---|
| 会话 | 独立 ZCode 会话/智能体实例 | 每个任务一个派发单元 |
| **写面** | **白名单写范围** | 当前主要隔离手段，见 §4.4 第 1 条 |
| 分支 | Git worktree 或分支 | 避免互相干扰；纪律见下 |
| 工作区 | DSH profile 隔离 | **未来阶段适用**（§4.6），非当前执行通道 |

#### 4.5.1 分支模型〔约束〕

| 分支 | 用途 | 规则 |
|---|---|---|
| `main` | 受保护主干 | **只经 PR 合入**；任何智能体**不得**直接推送（`AGENTS.md`「禁止直接推 main」）。CI 门禁为 PR 的 `verify` 检查 |
| `feat/BE-N-<主题>` | 后端切片开发 | 一片一分支，命名带切片号（如 `feat/BE-3-team-data-layer`）；便于按片复审与回退 |
| `fix/issue-N-<主题>` | 缺陷修复 | 命名带 Issue 号（如 `fix/issue-42-storage-lease`）；PR 必须关联该 Issue |
| `docs/<主题>` | 文档批次 | 多文档小改可合批（如 `docs/p2-contract-sync`）；仍走 PR |
| 其他工作分支 | 实验、重构等 | 同样走 PR；不得直接落 `main` |

**共同规则**：分支从最新 `main` 起；PR 关联 Issue；合并前过 CI（`format:check` / `lint` / `typecheck` / `test` / `build`）；提交信息符合 `AGENTS.md` 的 commit 规范（`<type>(<scope>): <描述>`）。

#### 4.5.2 worktree 纪律〔约束〕

> **规范正本在 [`AGENTS.md`](../../AGENTS.md) 的「Git 工作流 → 工作区（worktree）纪律」七条**（面向全体智能体的强制入口）。本节是它的**详细背景、事故记录与判据展开**；两者不一致时以 `AGENTS.md` 为准，并回来修正本节。

1. **建了就用**。worktree 一经建立，工作就在其中进行；**不得**建而不用后转为「滞留快照」。
   - **开工前先问：这个工作真的需要独立工作区吗？** 只有「需要与其他写者**并行**且写面互斥」或「候选需**冻结**独立验收」才建。**纯文档改动、单人顺序完成的同一主题**（如流程修订、契约条款修订）**不建 worktree**——在已有分支上直接改即可。
2. **完成即清理——「清理」是「建」的收尾动作，不是独立待办**。分支合并或任务终止后**立刻**清理；**不得**把删除拖到「本轮结束再统一处理」——那正是堆积的来源。
   - 〔实测，2026-09-18 两轮各犯一次〕第一轮留 4 个孤儿副本，第二轮又留 2 个已完成文档 worktree。**同一形状的错误重复出现 = 纪律没有被当成动作的一部分。**
   - **`git worktree remove` 只解除登记、不删除目录内容**（尤其 `node_modules` 下的 junction 会留在磁盘上形成**未登记的死目录**）。故清理是**两步**：① `git worktree remove <path>`；② 若目录仍在，**先逐个解除 junction/symlink（只删链接本身，不递归穿透；删前核对每个链接的目标是否落在该 worktree 内部）**，再删目录；最后复算 `git worktree list` **与** `ls .worktrees/` **两者**都干净。
3. **死目录必须清除**。`gitdir` 指向不存在路径的 worktree 目录（如 `.git` 文件写 `gitdir: <repo>/.git/worktrees/<name>` 而该路径不存在）会让 `git rev-parse HEAD` 报 `fatal: not a git repository`——**不得**把这种目录当作工作区使用，须清理。
4. **不得据滞留目录做交付判断**。目录内自述为「快照/非 worktree」的标记（如 `_STALE_SNAPSHOT.md`）即视为**非权威**，不得作为开发或验收依据。
5. **候选必须经分支提交，不得经文件拷贝合并**〔2026-09-18 补，来自实测事故〕。交付路径固定为：
   `写手在 worktree 内改动 → 指挥在**该 worktree 内** commit 到其分支 → push → PR → CI 绿 → merge`。
   **禁止**把候选文件从 worktree **拷贝**到主仓另一分支后提交——那样 worktree 里的原件会永远留在工作区成为「孤儿副本」，且**合并后无法用 `git merge-base` 判断它是否已交付**（`branch --merged` 只证明**分支指针**是祖先，而工作区改动**从未进入任何提交**）。
   〔实测〕2026-09-18：6 个 worktree 中 4 个的改动全部已进 `main`，但因采用拷贝合并，其工作区仍显示 12 处 `M`/`??`，且 `git branch --merged` 给出**误导性的「已合并」**结论。
   - **交付即冻结**：候选提交后**立即** push 并开 PR——**远端可读是本地目录可删的前提**。若候选只存在于本地 worktree，它就**不能**清理（外审无法读取）。
6. **合并后的清理判据：按内容判，不按指针判**〔约束〕。rebase 合并会**重写提交 hash**，故 `git merge-base --is-ancestor <branch> main` 对**已合并**分支可能返回假（分支独有 commit 数非 0）。**不得**仅凭 `branch --merged`、`git diff --stat` 的删除行数、或「分支名存在」判定可删。
   - 内容等价性证据二选一：**`git cherry main <branch>`** 全部输出 `-`（等价补丁已在 main）；或**逐文件比对**（对分支改动的每个文件核对 main 上的对应内容，须处理**新增 / 删除 / 重命名**与 main 后续的合法修改——**不得**只检查「main 中路径存在」）。
   - 〔**这两项只是「提交内容已交付」的证据之一，不是工作区可删除的充分条件**（2026-09-18 外审 Q6 修正）〕`git cherry` 比较的是**提交补丁等价**且忽略部分格式信息；它**不证明**以下任何一项已保存：**未提交改动、未跟踪文件、被 gitignore 的忽略资产（含证据与运行数据）、进程归属、junction/symlink 目标**。故清理判定必须**先做工作区盘点**（第 7 条），且 `git worktree remove` 对**不干净工作区**的默认拒绝**不得**被脚本用 `--force` 绕过。
   - **托管 CI 看不到开发机的实际未提交目录**，不能承担「工作区可安全删除」的证明。**证据不足即保留。**
7. **清理动作留证据 + 先用只读盘点**。删除 worktree / 分支前**先跑一次只读盘点**（脚本或手工），逐项列出：worktree 路径、分支/HEAD、**暂存 / 未暂存 / 未跟踪**内容、需保留的**忽略资产**（`.artifacts/` 下的证据与运行数据）、关联 PR 与候选身份、**进程与资源归属**（是否有进程仍在使用该目录）、以及 Windows `junction`/`symlink` 的**链接本身与目标**（不递归穿透到共享依赖或用户数据）。盘点给出三档结论：**可清理 / 必须保留 / 证据不足**，**默认不删除**；执行前复核状态未变化，再由受控操作清理并留前后记录。删除后复算 `git worktree list` 与 `git branch` 确认登记已解除。
   - 清理工具**只做本地只读盘点与计划**，不抢占正确性修复与业务闭环的关键路径；**不得**用 `--force`、`clean` 或空目录镜像把「证据不足」变成「看起来干净」。

> **实例记录（2026-09-18，仅作纪律背景）**：`docs/operations/environment-handoff.md` 于 2026-09-16 声明 SoloIPs 候选位于 `.worktrees/team`、分支 `codex/team-fork-integration`。2026-09-18 盘点实测：该分支**在所有 ref 中不存在**，`.worktrees/team` **不是 git 登记的 worktree**（`gitdir` 指向不存在的 `.git/worktrees/team`），目录内 `_STALE_SNAPSHOT.md` 自述为非 worktree 快照。即**建了未用、遗留死目录**——正是本节纪律要避免的情形。详见 `.artifacts/operations/environment.local.md` §9.1 C2。

#### 4.5.2.1 进度观测与时间型检查点（2026-09-18 补，来自外审 Q3/Q4）〔约束〕

**背景**：BE-6a 切片出现 41 分钟零产出侦察，指挥用「每 5 分钟扫文件 + 4 次发消息催办」应对，结果**更慢**。外审判定：根因不是「0 行代码」，而是**没有「何时必须交付可证伪中间结论」的检查点**；且「发消息催办」对子智能体是**打断**——它必须开新回合处理，挤掉正在做的工作。

**一、时间型检查点（写手侧，强制）**

适用于 L2/L3 片（依赖已冻结、有既有骨架可参照的接线/实现类）。**里程碑对象是「可核验增量」，不是代码行数**：

| 时点 | 必须交付 | 合格增量的形态（任一即可） |
|---|---|---|
| **T+15 分钟** | **第一份 checkpoint** | ① 已确认的文件/调用链；② 一个**可证伪的假设**；③ 最小失败复现或探针；④ 下一动作 |
| **T+30 分钟** | 若仍无可验证增量 | **停止泛搜**，缩小问题 / 派专门探针 / 上报指挥裁定。**不是**「30 分钟没写代码就强制开始乱改」 |

- 真正陌生的 L4 架构调查可放宽**总时长**，但 checkpoint 机制**保持**。
- 「侦察阶段产出零代码」本身**不是缺陷**——缺的是中间结论的交付义务。

**二、指挥侧观测：低频、结构化、被动**

**「文件的 mtime + `git status`」不够**——它只能回答「有没有文件变化」，无法区分「在正确侦察」/「重复撞墙」/「正在跑长命令」/「在错误路径上产生代码」。**「mtime 在动」与「走在正确路径」是两回事。**

改为**结构化状态 + 低频被动读取**：

| 观测对象 | 内容 |
|---|---|
| `phase` | recon / repro / implement / verify / blocked |
| `hypothesis` | 当前正在证伪什么 |
| `last_command` + `last_exit` | 最近一条关键命令与其退出码/失败摘要 |
| `diff_summary` | 改了哪些事实面 |
| `evidence` | 探针 / 报告路径 |
| `blocker` | 若阻塞，阻塞在哪一层 |
| `next_action` | 下一步 |

**接触纪律**（对应用户 2026-09-18 的明确批评）：

1. **派发时把要求一次写完整**——包括之后可能想到的补充。事后追加 = 打断。
2. **派发后不主动发消息**。只读观测（`git status` / 文件 mtime / 产物 / 结构化状态）**不打断**；`SendMessage` **才**打断。
3. **仅三种情形接触**：① 子智能体主动报告完成或阻塞；② 产出需要指挥裁定且它已明确请求；③ 指挥作为 git 管理员要提交。
4. **指挥每 15–20 分钟或 phase 转换被动读取一次**即可；仅在 `blocked` / 红线 / 超 budget 时主动介入。
5. 判断任务确实卡住时：**换线重开**（停掉、保留产出、重派并设硬 checkpoint），**而不是连续催办**。

> **实测代价（2026-09-18 BE-6a）**：写手会话 1h55m，其中 41 分钟空转侦察 + 被指挥 4 次打断。指挥与外审一致判定：**频繁打断使任务更慢**。

#### 4.5.2.2 根因因果状态分层〔约束〕（2026-09-19 补，来自外审）

**纪律**：缺陷报告**不得**从「发现一个相关异常」直接跳到「根因已定位」。每个断言必须标注所处层级：

| 状态 | 允许的表述 |
|---|---|
| Observed | 观察到错误 X |
| Reproduced | 可稳定复现 X |
| Correlated defect | 同时发现了缺陷 Y |
| Hypothesis | Y 可能导致 X |
| **Causally verified** | **单变量**移除 Y 后 X 消失；恢复 Y 后 X 重现 |
| Closed | 候选经原真实消费者路径通过，且有回归门 |

**只有达到 `Causally verified` 才可写「根因」**；此前一律写「相关缺陷 + 假设」。

〔实测事故，2026-09-19 BE-6a〕三层缺陷依次被误当「根因」：①产物双类定义（真实缺陷，但修复后 E2E 仍红 → 反证非充分因）；②cordis Proxy 私有成员访问（单变量验证后成立）；③web 行 `inject` 缺位（单变量验证后成立）。每次「看起来解释得通」的异常都曾中止进一步排查。

#### 4.5.2.3 候选证据身份绑定〔约束〕（2026-09-19 补，来自外审）

放行对象是**不可拆元组**，不是「PR 绿了」：

```
candidate SHA + 产物 digest + runtime 指纹 + E2E 证据 digest + QA 判定 + CI run id
```

- **任一元素对应的 SHA 变化 → 真实链路证据自动 stale**；不得由人判断「这次改动应该不影响」。
- merge / rebase / 构建输入变化后，真实消费者证据**必须重跑**。
- 证据落盘格式须含上述绑定字段与 `stale 规则`的显式声明。

#### 4.5.2.4 liveness / progress / ownership 三信号分离〔约束〕（2026-09-19 补，来自外审）

「是否活着」「是否有进展」「谁有权写」是**三个独立问题**，不得用单一信号回答：

| 信号 | 判据 |
|---|---|
| **liveness** | 完成通知（权威）/ 进程存活 + heartbeat 时间戳 |
| **progress** | 结构化状态：`phase` / `hypothesis` / `last_command+exit` / `evidence` / `blocker` / `next_action` |
| **ownership** | worktree **单写者 lease**（令牌）；接管须见旧 lease 明确释放或指挥判定过期，再换新令牌 |

〔实测事故〕2026-09-19：指挥据文件 metadata 误判会话已死 → **向同一 worktree 重复派发**（两个写手同写面）。「只认完成通知」修正了误判方向，但**不足以**检测死锁 / 崩溃 / 长停滞；故必须补 ownership lease 与结构化 progress 两层。

#### 4.5.3 指挥是 git 管理员〔约束〕

| 职责 | 要求 |
|---|---|
| 审查后提交 | 子智能体改动经指挥审查后由**指挥统一 commit**（§4.4 第 4 条）。指挥不得把未审查的改动直接提交 |
| 及时分批 | **按逻辑单元分批提交**，不留长期未提交的大堆改动；一批一主题，提交信息能独立解释 |
| 提交信息 | 符合 `AGENTS.md` 的 `<type>(<scope>): <描述>`；正文写清动因与证据边界 |
| 分支收口 | 任务完成后走 PR；确认 CI 通过再合入 `main` |
| 不代子智能体提交 | 子智能体**一律禁 `commit` / `push`**（含 `--amend`、`rebase` 等改写历史的动作） |

#### 4.5.4 「临时解除保护 → 推 → 恢复」的使用纪律〔约束〕

该动作序列（暂时放开 `main` 保护、直接推、再恢复保护）**仅限用户明确授权的重置场景**，典型为：仓库需要回退/重建历史、修复无法经 PR 走通的仓库状态。

| 条件 | 要求 |
|---|---|
| 授权 | **必须有用户对该次动作的明确授权**；历史授权不覆盖新的重置（`AGENTS.md`「历史授权只覆盖原任务范围」） |
| 记录 | 授权来源、动作前后 SHA、受影响分支与恢复结果须留痕 |
| 禁止 | **不得**把它当作绕过 CI 或绕过 PR 审查的捷径；常规开发一律走 PR |
| 环境状态 | 环境变化（如 CI 故障）**不构成**该授权的来源（`AGENTS.md`「环境状态变化不能创建或扩大授权」） |

### 5.2.1 完成判据：客观标尺（2026-09-18 补）〔约束〕

**为什么需要这一节**：首轮开发暴露的失败**全部是同一个形状**——「看起来完成了」≠「完成了」。以下每条判据都来自一次**实测事故**，且每条**可机器核对**（不接受主观陈述）。

#### A. 候选冻结与身份一致

| # | 判据 | 如何核对 | 事故来源 |
|---|---|---|---|
| A1 | 冻结时记录 **diff SHA + 新增文件 SHA** | `git diff \| sha256sum`；新增文件逐个 sha256 | — |
| A2 | **验证期间候选不得变动** | 验收开始与结束各复算一次 SHA；不等即旧结论作废 | — |
| A3 | 验证后若源码被改（**含注释**），旧结论不得沿用 | 须重新验证；**或**在独立复核确认影响范围后**复用**证据——复用必须说明**复用哪一层**（只在语义层？还是也覆盖类型/生成物/声明/发布元数据） | BE-5：冻结后补注释 |
| A3.1 | 每次字节变化都生成**新候选身份**（新 SHA）；但不等于任何变化都**全量重跑**——按影响决定复验范围 | 身份须覆盖：base、已跟踪变更、**暂存区**、**未跟踪新增文件**、路径与**删除**；并关联锁文件、构建输入与环境标识。单独 `git diff \| sha256sum` **不覆盖**这些 | BE-5 冻结控制失效 |
| A4 | 「去注释后相同」**只作辅助比对**，**不是**通用等价证明 | `removeComments` 是 JS 输出选项；注释可能影响编译指令（如**三斜线注释**）、类型检查、生成器、声明与发布元数据。CRLF 归一化只适用于明确的文本比较范围，**不得**改变用于 digest / 构建再现的输入定义（外审 Q3） | BE-5 |

#### B. 「绿」必须绑定真实断言

**核心命题：门禁/测试「绿」不构成证据，除非同时给出「它会红」的证据。**

| # | 判据 | 如何核对 | 事故来源 |
|---|---|---|---|
| B1 | **每个新增或翻新的门禁必须附反例**：施加目标变异 → 该门变红 | 变异 → exit 1 → 还原 → exit 0，全留日志 | BE-0b-i/BE-0b-ii 多轮 |
| B2 | **接线断言必须证明期望路径确实执行**，不能只匹配文本 | 纯字符串 `toContain` 不合格（注释、死分支可满足）；但 AST 找出调用节点**也只是发现语法节点，不自动证明被执行**。最强证据是**执行**：让该路径真的跑一次并观察效果（外审 Q1/Q7） | QA 实测：注释/死分支可满足子串匹配；AST 无执行语义 |
| B3 | **在门禁「声称覆盖或替代」的那部分契约面上**，判据强度必须 ≥ 运行时判据 | 若门禁在该面上比运行时**宽**（漏检而运行时会抛错）→ 真实漏检，须对齐。**不要求**一个局部静态检查复制整个运行时（外审 Q7） | 盲区 3：`parameters ?? []` 静默跳过 vs 运行时 `requireArray` 抛错 |
| B4 | **防空集守卫**：被检查的对象集合为空时必须 FAIL | 防「形态变更后检查退化为空转」 | BE-0b-ii；BE-5 E8b 同源 |
| B5 | **「声明的期望集合」须与「实际产物 / 入口集合」双向核对** | 只从文件系统枚举现存文件会漏掉**本来应该存在却丢失**的文件；只用手写清单会漏列新增项。二者**都要**：期望集合非空 + 实际集合 ⊆ 期望（无未登记对象）+ 期望 ⊆ 实际（无缺失对象） | 盲区 2：从清单删条目双绿（外审 Q7 修正） |
| B6 | **变异体区分「击杀」与「破损」** | `ReferenceError`/未用变量/语法错 = **破损变异体**，不计击杀；须重写为单变量语义变异。**准确归属**：验证**类型契约**时，预期的类型拒绝可以是有效证据；验证**运行时语义**时，仅类型失败不够。等价变异须说明**等价条件**，不为凑「全杀」写无价值断言 | BE-5 M2/M3 首版 199 条 `ReferenceError`；外审 Q1 补充 |
| B7 | **哪些门必须有反例**：**每个新建 / 实质修改、且被依赖为放行依据的自定义门禁**，至少证明一次「正向能过 + 目标违规能拒」。**不要求**每个普通断言都配变异，也不要求每轮重跑全部历史变异 | 目标违规是什么 → fixture/变异有效 → 真正到达目标检查 → 因**预期语义**失败 → 还原后通过。反例可以是正常维护的负向测试，不必全做临时源码变异 | 外审 Q1 |
| B8 | **止损 = 停止错误的修补方式，不是停止发现问题** | 同一门禁**连续两次同类失效**即触发一次**有边界的根因复核**：检查对象是否错？是否造了一个**弱于真实消费者**的验证器？能否直接复用真实加载/调用？**它不是「两轮以后带缺陷放行」的配额** | 0b-ii 多次重做同一验证器（外审 Q1） |

### 5.2.2 主流程完成条件（六条，收敛口径）

〔为什么收敛为六条（2026-09-18 外审 Q7）〕原 §5.2.1 的 A–F 六组是**判据库**（按需查阅），不是每个任务的强制清单。**主流程只保留六条完成条件**；原理、实验过程与历史事故放进对应专题或不可变报告，模板只**链接**，不把每起事故复制进每个任务。

1. **范围与验收条款已核销**，未完成项有明确的阻塞或批准归属。
2. **被验候选、实际提交与交付产物身份一致**。
3. **独立 QA 完成风险对应的验证**，关键放行门**没有已知空转**。
4. **最终 CI 与适用的真实运行证据有效**，未知结果**如实保留**。
5. **契约、实现状态与后续责任同步**，证据可读。
6. **任务自有资源已安全交接或清理**，未知 / 在途资产不删除。

### 5.2.3 高后果裁定须先取独立视角（轻量，非常驻席位）

〔触发条件（外审 Q5）〕**只给高后果或高不确定性的裁定**加独立复核：新增/放宽**持久化、并发、重放、信任边界**约束，以及**删除数据、接受已知风险、认定候选等价**。格式修正、既定模式下的普通拆分、无业务影响的措辞**不需**再走一套流程。

提交材料**一页**即可：当前事实与固定源码 → 要裁定的 A/B → 各自保护的不变量 → 最强反例 → 影响范围 → 推荐与遗留。QA 可做一次**定向探针**；契约边界交外审。

〔**风险按语义分级，不按扩展名**〕改的是 Markdown **不**等于低风险——若它改变的是持久化/并发/信任边界的**约定**，就走高风险语义审查。

#### 指挥自检（轻量，不作流程门）

**派发前 5 问**：① 可验收出口是什么（单一、可观察）？② 依赖的前置是否已就位？③ 写面白名单是否与在途工作互斥？④ 风险级别与验收深度匹配吗？⑤ 阻塞上报通道写在工单里了吗？

**汇报前 3 问**：① 结论**每条**都有证据吗（含「否定性结论」的多词复核）？② 我有没有把「过程的完成」当成「目标的完成」？③ 数字与 SHA 是可追溯来源吗——**指挥核验来源与适用性即可，不必亲自重复 Q 已有效执行的同一运行**（外审 Q7 修正）？
