## 1. 开发模式定义

### 1.1 核心原则

```
一个会话 = 一个任务 = 对应难度选择模型
```

| 角色 | 职责 | 模型选择 | 说明 |
|---|---|---|---|
| **主会话（指挥）** | 统筹协调、任务分配、结果审查、质量把关 | **Fable 5.1** | 编码73.4%、科学推理52.6%、更便宜更快 |
| **子 Agent** | 执行具体开发任务、代码实现、单元测试 | 通过 DSH 派发 | DSH 使用 newapi 配置的模型 |

### 1.2 模型配置

```yaml
# newapi 模型配置（位于 .zcode/newapi-providers.yaml）
# DSH 直接使用 newapi 配置的模型

models:
  # 主会话模型（指挥）- Fable 5.1 全面优于 Opus 5
  # 注意：模型 ID 必须与 newapi 配置一致（见 DSH Web UI 模型下拉菜单）
  main: "claude-fable-5-1"              # 默认指挥模型（1M版本，开启思考）
  main_safe: "claude-opus-5"              # 仅高安全需求时（1M版本）

  # 子 Agent 模型（通过 DSH 派发）
  # 模型由 newapi 配置决定，不需要在文档中单独指定
```

> **重要**：模型 ID 必须与 DSH newapi provider 配置一致。可用模型包括：
> - `claude-fable-5-1`（显示为 `[G]claude-fable-5-1（1M）`）- **推荐使用**
> - `claude-opus-5`（显示为 `[G]claude-opus-5（1M）`）
> - `claude-fable-5-thinking`（显示为 `[G]claude-fable-5-thinking`）
> - `claude-opus-5-thinking`（显示为 `[G]claude-opus-5-thinking`）
>
> **推荐配置**：使用 1M 版本（claude-fable-5-1 / claude-opus-5），在 DSH 中开启思考模式使用。

### 1.3 Fable 5.1 vs Opus 5 性能对比

| 基准测试 | Fable 5.1 | Opus 5 | 差距 |
|---------|-----------|--------|------|
| Terminal-Bench-Science (科学推理) | **52.6%** | 29.0% | +23.6% |
| CursorBench (代理编码) | **73.4%** | 70.0% | +3.4% |
| Humanity's Last Exam (多学科推理) | **65.0%** | 63.6% | +1.4% |
| Terminal-Bench 4.0 (终端编码) | **55.8%** | 42.0% | +13.8% |
| AutomationBench (业务流程) | **31.4%** | 26.9% | +4.5% |

**结论**：Fable 5.1 在开发相关任务上全面领先，价格更低、速度更快。Opus 5 仅在高安全级别场景保留。

### 1.4 思考强度配置

| 强度 | 使用场景 | 说明 |
|---|---|---|
| `high` | 系统设计、跨模块重构、新技术引入 | 深度推理（仅必要时） |
| `medium` | **默认**，包括架构设计、复杂决策、代码实现 | Fable 速度快，medium 性价比最高 |
| `low` | 简单确认、格式调整、文档整理 | 快速执行 |
| `off` | **禁止使用** | 不适用于开发场景 |
| `max` | **禁止使用** | 浪费资源 |

## 2. 任务难度分级

### 2.1 难度定义

| 等级 | 任务特征 | 指挥模型 | 思考强度 | 子 Agent 数量 |
|---|---|---|---|---|
| **L1 简单** | 文档整理、单文件修改、格式调整 | Fable | `low` | 1个 |
| **L2 标准** | 功能实现、单元测试、简单重构 | Fable | `medium` | 1-2个 |
| **L3 复杂** | 多包协调、API设计、性能优化 | **Fable** | `medium` | 2-3个 |
| **L4 架构** | 系统设计、跨模块重构、新技术引入 | **Fable** | `high` | 3+个 |

> **注意**：L3-L4 原本用 Opus，现在改用 Fable，因为 Fable 5.1 在编码任务上全面领先。Opus 仅在高安全场景保留。

### 2.2 难度判断标准

```
L1: 单文件改动 < 100行
L2: 单包改动，功能边界清晰，有明确验收标准
L3: 多包改动，涉及接口变更，需要协调
L4: 新系统/子系统设计，影响多个团队/模块
```

## 3. 智能体协作流程

### 3.1 主会话流程

```
┌─────────────────────────────────────────────────────────────┐
│                      主会话（指挥）                          │
│                    Fable 5.1（默认）                         │
│                                                             │
│  1. 接收任务                                               │
│      ↓                                                     │
│  2. 评估难度 → 选择指挥模型 + 思考强度                     │
│      ↓                                                     │
│  3. 任务分解 → 子任务 + 依赖关系                           │
│      ↓                                                     │
│  4. 派发子 Agent → 分配模型 + 思考强度                     │
│      ↓                                                     │
│  5. 收集结果 → 审查 + 整合                                 │
│      ↓                                                     │
│  6. 输出最终交付物                                         │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 子 Agent 执行流程

```
┌─────────────────────────────────────────────────────────────┐
│                    子 Agent                              │
│                                                             │
│  1. 接收任务描述 + 验收标准                                │
│      ↓                                                     │
│  2. 执行任务（代码/文档/测试）                             │
│      ↓                                                     │
│  3. 自我审查（符合规范？）                                 │
│      ↓                                                     │
│  4. 返回结果 + 证据（文件变更、测试结果）                   │
└─────────────────────────────────────────────────────────────┘
```

### 3.3 协作模式

| 模式 | 使用场景 | 子 Agent 数量 |
|---|---|---|
| **串行** | 任务有强依赖，必须按序执行 | 1 |
| **并行** | 独立子任务，可同时执行 | 2-4 |
| **流水线** | 前一个输出作为后一个输入 | 2-3 |


| 工作区 | DSH profile 隔离 | soloips / 其他 |

## 5. 质量保障

### 5.1 审查机制

| 审查点 | 执行者 | 时机 |
|---|---|---|
| 子任务完成审查 | 主会话 | 每个子 Agent 返回后 |
| 集成审查 | 主会话 | 所有子任务完成后 |
| 规范审查 | 主会话 | 提交前 |

### 5.2 审查检查清单

- [ ] 代码符合 TypeScript strict 模式
- [ ] 无 `any` 类型
- [ ] 符合包边界规则
- [ ] 测试通过
- [ ] 文档已更新

### 5.3 回退机制

| 失败情况 | 处理方式 |
|---|---|
| 子 Agent 执行失败 | 记录错误，重新派发（最多3次） |
| 集成失败 | 主会话接管，修复后继续 |
| 多次失败 | 通知用户，等待决策 |

### 9.7 验收原则

1. **安装 ≠ 调用**：包安装了不等于功能可用
2. **构建 ≠ 验收**：代码构建成功不等于用户成果
3. **源码 ≠ 版本**：源码改了不等于目标安装已更新
4. **验收分层**：安装 → 装配 → 调用 → 验收 层层验证

### 10.3 Agent 执行规范

每个子 Agent 必须遵守以下规范：

#### 5.1 启动时必须做

1. **读取规范文档**（按顺序）：
   - `docs/governance/code-development-standard.md`
   - `docs/technical/packages.md`
   - 相关架构文档

2. **确认配置**：
   - 模型: `claude-fable-5-1`
   - 思考: `medium` 或 `high`
   - 包路径: 按任务分配

3. **确认任务范围**：
   - 验收标准
   - 禁止事项
   - 输出要求

#### 5.2 执行时必须做

1. **定期报告进度**：
   - 完成每个子任务时报告
   - 遇到问题立即报告

2. **遵守代码规范**：
   - TypeScript strict 模式
   - 无 any、无 @ts-ignore
   - ESM 模块

3. **记录变更**：
   - 变更文件列表
   - 测试结果
   - 问题日志

#### 5.3 完成后必须做

1. **自检**：
   - `pnpm run typecheck` 通过
   - `pnpm run lint` 通过
   - `pnpm run build` 通过

2. **提交报告**：
   - 变更文件列表
   - 验收标准对照
   - 遗留问题
