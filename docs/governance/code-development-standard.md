## 0. 适用与开工边界

**〔约束，DEV-01〕** 开发者开始一个代码切片前，必须核对用户授权、对应需求 ID、实际入口、交付目标和一条可观察的验收样例。需求与授权以最新用户指令及项目绑定为准；包职责、装配和数据机制以技术架构为准；本文规定如何编写与验证代码。发现冲突时先追溯该条权威，不用代码实现反向确认需求。

**官方协作复用范围：** [SOLO-TEAM-FORK](../decisions/official-team-and-dsh-fork.md) 是官方 Team / subagent / Session 复用及 DSH fork 的专题正文。DEV-03/04/08 的 core 写权与唯一 opener 限定 SoloIPs 业务事实；官方协作的最终提交由 Team 权威负责，适用准入、审核和失权检查须覆盖真实提交点，不能只在可绕过的 core 外层检查。旧参考代码的具体状态布局不覆盖该决定。

- 文档任务交付文档；产品实现、运行探针、服务或部署变更分别遵守既有授权。本文不启动 S0。
- 获授权实现后，按 ARCH-D06 使用真实原生任务记录范围、写者、结果与资源归属；配置能力以项目绑定为准，不虚构已建立的任务或 CI。
- 技术选择由负责该切片的开发者在已定边界内解决。需要改变业务目标、扩大副作用或推翻已定架构时，才提交具体差异与证据供裁定。

## 1. 语言、工具与格式

**〔约束，DEV-02〕** 首次建立代码工具链的开发者必须采用下表基线，并在同一切片交付可执行配置。后续命令与精确版本的唯一正文是仓库配置；本文不维护第二份版本清单。

| 项 | 工程规则 | 验证入口 |
| --- | --- | --- |
| 语言与模块 | 业务与适配代码使用 TypeScript、ESM；Web 组件使用 TSX 并沿用所选 DSH client 的 React 兼容组合 | 包 `type`、`exports` 与 host/client 构建结果 |
| 包与依赖 | 开发 workspace 使用 pnpm 与统一锁文件；交付 profile 是独立安装 workspace，需对应的 profile 锁，开发根锁不能代替它。Node 与 pnpm 各锁定一个经目标宿主验证的精确验收版本；统一交付组合遵守 ARCH-D02，具体 profile 锁落点结合 SOLO-C05 验证 | 各 workspace 的 `packageManager`、Node 版本配置、`pnpm-lock.yaml` 与安装记录 |
| 类型检查 | 开启 `strict`、`noUncheckedIndexedAccess`、`exactOptionalPropertyTypes`、`noImplicitOverride`、`noFallthroughCasesInSwitch`；host/client 分别限制平台类型与入口 | 共享 tsconfig 与各包 typecheck |
| 静态检查与测试 | 使用 Oxlint、Vitest；格式化使用 Prettier。工具版本由锁文件固定；不复制上游整套发布脚本与原生构建流程 | 根脚本及对应工具配置 |
| 文本 | UTF-8、LF、文件末尾换行；TS/TSX 两空格缩进、双引号、分号，格式化配置为具体排版权威 | EditorConfig、formatter；第三方保留文件按来源约定 |

默认验证命令由首个实现切片提供；下面是**应建立的接口**，不是已经执行的结果：

| 命令 | 必须实际完成的检查 |
| --- | --- |
| `pnpm install --frozen-lockfile` | 按提交的锁文件安装；依赖更新在开发中显式改锁，验收时冻结 |
| `pnpm run format:check` | 受管源码与配置的格式；修复命令不得顺手重排无关历史文档 |
| `pnpm run lint` | 静态规则及受管源码的 host/client 边界 |
| `pnpm run typecheck` | host/client 与公开契约类型，不以打包器转译代替 |
| `pnpm run test` | 确定性的本地单元与契约测试，默认不访问真实外部服务 |
| `pnpm run build` | 生成本切片所交付包的实际工件，检查声明和入口 |

没有入口或尚不能运行时，开发者应完成所需配置或在任务中记录具体缺口；不得用空脚本、跳过全部用例或始终返回成功填充门禁。集成/真实 Host 验收按切片增加明确入口，不让默认测试偷偷使用用户会话、生产数据或付费 API。代码切片交付前运行适用的格式、静态、类型、测试与构建检查，允许按受影响包收窄范围。

**开发运行实例的安装边界：** [DEVENV-01–02](../operations/development-iterations.md) 的研发实例可采用官方打包验收使用的 npm tarball 消费方式：`runtime/package-lock.json` 锁定宿主依赖，Profile 自身的 `package-lock.json` 锁定外部 bundle 安装；bundles、patch 与 preset 同时由版本清单校验哈希。先安装 runtime，再安装 Profile；官方生成的模块代理只能指向本版本固定 runtime，不能指向开发源码或其他版本。在 `release.json` 记录实际 Node/npm 版本与安装方式。此例外限定开发实例，不改变 SoloIPs 源码 workspace 的 pnpm 工具链，也不提前宣布下节产品 Profile 交付锁已完成。

## 2. 目录、依赖与公开接口

**〔约束，DEV-03〕** 新代码按技术架构 ARCH-D02 的包职责放入 `packages/<包名>/`；只创建当前切片实际需要的文件。S0 交付所需四包，`tools-pv` 随 S1 加入。包内以能力组织；边界入口、领域规则、适配与视图在产生职责差异时分文件，不按空模板预建目录或通用框架。

**〔约束，DEV-04〕** 开发者增加 import、插件声明或服务调用时，必须同时满足下列边界，评审者检查源码依赖与实际打包内容：

- 包间使用明确的 `exports` 与服务契约，禁止跨包相对路径、邻仓源码别名和运行工件中的 `src/*` 深层导入。`exports` 暴露源码路径也不能替代稳定发布接口。
- `adapter-dsh` 收敛 Host 对 DSH storage、session、subagent、tools 等执行能力的适配；业务规则由 core 消费内部接口。core 持有业务 domain 的唯一 opener 与写入口；adapter 不另持业务权威。
- Web 可以使用 DSH 官方公开 client/UI 扩展 API；各插件入口可以使用公开的插件注册接口及类型。此例外不允许 client 引入 Host 实现、文件系统、凭据或 domain handle。
- web 读 Host 投影，通过经授权的命令入口提交意图；tools-pv 经 core 服务保存 job 与结果。服务必须再次验证身份、资格与状态，不能把调用方自报的员工 ID 当授权。
- 同步编译依赖不得成环。反向结果用服务契约或事件传递；类型放在实际拥有该契约的现有包公开入口，不为消除一个 import 环就新增第六个包。
- 必需服务用 DSH 的公开注入与就绪约定声明；不依赖 YAML 行序、任意延时或全局变量猜测初始化完成。bundle 只承载装配声明，配置顺序及完整覆盖语义引用技术架构 SOLO-C01。

首个包、公开接口变更和依赖升级必须验证打包后安装入口：在隔离环境安装所交付工件，确认无个人 `file:`/`link:` 路径、邻仓源码或未声明传递依赖。Host/client 共享依赖的打包或外置方式按 DSH 公开加载契约选择并验证，防止出现两套运行实例。

### 2.1 根目录与包目录（DEV-03 的落地约定）

**〔约束〕** 以下布局承接 ARCH-D02、DEV-02/03；来源为用户要求补齐开发前文档与各插件包目录。它是首个获授权实现切片的布局设计，**不表示目录或配置已经创建**。实际需要时才建文件；S0 最终交付前四包，S1 才创建 tools-pv，领域子目录随具体行为出现。

```text
soloips/
├── AGENTS.md
├── docs/                         # 已登记的规则、设计与交接规程
├── .agents/skills/               # 官方文档导航等开发技能
├── package.json                 # private 开发根、工具版本和实际检查命令
├── pnpm-workspace.yaml          # 开发成员仅 packages/*
├── pnpm-lock.yaml               # 开发 workspace 锁
├── tsconfig.base.json           # 共享严格类型规则
├── tsconfig.json                # 根检查入口；Host/Client 分别配置
├── .editorconfig
├── .oxlintrc.json
├── vitest.config.ts
├── packages/
│   ├── soloips-bundle/           # package.json、cordis.patch.yml、相关装配测试
│   ├── soloips-adapter-dsh/      # Host 适配及其公开契约
│   ├── soloips-core/             # 唯一业务写入口与持久状态
│   ├── soloips-web/              # Host 桥和独立 Client 入口
│   └── soloips-tools-pv/         # S1 才加入
├── profiles/soloips/            # 可移植的交付定义与独立 profile 锁
├── .worktrees/                  # 需要隔离时创建；不入库
└── .artifacts/operations/       # 本机交接记录；不入库
```

- DEV-02 的格式化规则由根 formatter 配置承载，采用独立文件或 `package.json` 字段均可；不要为凑齐文件名同时维护两份。`.npmrc` 仅在所选依赖/安装方式确实需要项目设置时建立，不能写入凭据。
- `profiles/soloips/` 是版本控制内的可移植定义与验收锁；实际运行 profile 仍位于获准的 `DSH_HOME/profiles/soloips`。它不加入 `packages/*` 开发 workspace：其依赖与锁须由交付工件在独立安装上下文解析，再以冻结锁重现，不能拿开发根锁冒充。各环境的实际 home、overlay、Session、业务和资产根按[环境交接](../operations/environment-handoff.md)绑定。
- `profiles/development/` 是 DEVENV 开发 preset 模板及无密钥验证入口，与产品 `profiles/soloips/` 分别交付。其消费实例的安装锁按 DEV-02 开发运行例外维护，模板目录不伪造尚未交付的产品依赖锁。
- 打包与配置行为先查[官方文档导航](../../.agents/skills/dsh-plugin-development/SKILL.md)对应版本。交付定义包含 profile manifest、需要的 patch 与独立锁，不包含用户会话、生产状态或机器绝对路径；初始化和安装方式随首片验证。宿主生成的 `cordis.yml` 不作为手工配置权威。
- 源码、测试与受版本控制的交付定义进入仓库；编译产物、依赖、临时 home 与本机记录按忽略规则隔离。根 `scripts/`、共享测试夹具及 `.github/workflows/` 仅在有实际用途时创建，不能用空目录或空脚本宣称工程已就绪。

### 2.2 每包的入口与文件职责

下表中的文件组织属于 DEV-03；公开依赖仍受 DEV-04 约束。所有进入 SOLO-C01 `bundles` 的包须实际声明 `dsh.bundle.patch` 并提供相应 `cordis.patch.yml`。下表的 `src` 是开发源码，`exports` 指向打包后的公开工件，Host 与 Client 的产物格式须以目标 DSH 公开加载契约验证。

| 包目录 | 最小文件与按需扩展 | 公开入口及验证重点 |
| --- | --- | --- |
| `packages/soloips-bundle/` | `package.json`、`cordis.patch.yml`；配置回归放 `tests/` | 仅装配声明，无运行时 `src/index.ts`；检查 patch 随工件发布、引用的能力包已安装、覆写顺序符合 SOLO-C01 |
| `packages/soloips-adapter-dsh/` | `package.json`、`cordis.patch.yml`、`src/index.ts`；需要共享端口时增 `src/contracts.ts`；适配按实际能力拆文件，测试放 `tests/` | `.` 为 Host 入口；按需公开 `./contracts`。契约由 adapter 拥有，不能反向 import core 形成环；不持有业务 domain handle |
| `packages/soloips-core/` | `package.json`、`cordis.patch.yml`、`src/index.ts`、`src/contracts.ts`；当前切片需要的 `src/company/`、`src/collaboration/`、`src/persistence/` 与 `tests/` | `.` 为 Host 入口；`./contracts` 只暴露浏览器安全 DTO/类型。SoloIPs 业务命令与提交归 core；collaboration 只承载业务绑定 / 规则，不另建官方 Team 状态机；IP/作品模块随相应切片增加 |
| `packages/soloips-web/` | `package.json`、`cordis.patch.yml`、`src/index.ts`（Host 桥）、`src/client/index.ts`（Client 注册）、实际 `.tsx` 组件与 `tests/` | 公开 `.` 与 `./client`，声明并验证 `dsh.client`。Client 读投影、经 Host 提交意图；Host 重新鉴权并调用 core 命令，不另存业务权威 |
| `packages/soloips-tools-pv/` | S1 创建 `package.json`、`cordis.patch.yml`、`src/index.ts`、具体制作工具适配与 `tests/` | `.` 为工具 Host 入口；通过 adapter 调用获准能力、通过 core 命令保存 job/产物；不获取 domain handle |

**依赖方向**：`core → adapter → DSH 官方 Host API`；`web Host → core`；`web Client → DSH 官方 Client API + core 的安全契约`；`tools-pv → adapter + core 命令契约`。同一公开入口不可把 core 的 Host 服务实现、Node 依赖或存储句柄带进浏览器；只需类型时使用类型导入。bundle 无业务运行时 import，但 profile 必须安装 patch 引用的完整能力集合。服务就绪仍通过注入契约验证，不能用以上箭头或目录顺序代替。

**包级文档按需生长**：包出现可消费接口时，在该包 README 简述职责、公开入口、配置、错误与适用验证，并链接需求/验收 ID。字段、schema 和函数签名以代码公开契约为准，不提前维护一份全量手写清单。只有实际出现需要长期解释的替代选择或难以逆转的决定，才补 ADR 或更新已有决定；不为每包预建一套 ADR。

## 3. 编码与接口契约

**〔约束，DEV-05〕** 作者与评审者按以下可观察行为检查新增或实质修改的代码：

| 方面 | 规则 |
| --- | --- |
| 命名 | 函数与变量用 `camelCase`，类型/类/React 组件用 `PascalCase`；普通模块文件 `kebab-case.ts`，组件文件 `PascalCase.tsx`；既有稳定 API 不为统一风格改名 |
| 职责 | 一个函数完成一个明确行为；权限、状态转换与持久提交的先后关系须可追踪。重复规则优先归到既有权威模块，不建立万能 util、第二套调度器或隐式全局注册表 |
| 类型 | 对外接口写明输入、返回与异步结果；不受信任数据先视为 `unknown` 并校验。禁止以 `any`、双重断言或 `@ts-ignore` 绕过业务校验；必要的外部类型缺口限于适配边界，须说明原因并有契约测试 |
| schema | 工具输入、API 请求、持久记录与外部结果在各自边界做运行期校验。DTO、类型及校验器保持一个维护来源，必要时派生或做契约校验；不维护三份手写且会漂移的字段定义 |
| 更新语义 | 显式区分字段缺省、清空与非法值；按 schema 定义处理未知字段。状态转换检查旧状态/revision，不把整个客户端对象直接覆盖权威记录 |
| 注释 | 解释不变量、取舍和失败语义，引用稳定需求/验收 ID；不复述语句。遗留项标明影响与跟踪入口，不留无上下文的“以后修” |

不得仅为满足任意行数或抽象层数拆分文件；当测试必须绕过大量无关状态、一次修改触及互不相关职责或依赖出现环时，才按实际边界拆分。

## 4. 异步、错误与资源生命周期

**〔约束，DEV-06〕** 创建异步任务、订阅、计时器、子进程或文件句柄的模块必须拥有其生命周期：等待任务结果，或登记到宿主可管理的任务生命周期中；关闭时停止接收新工作并释放资源。禁止无错误处理的游离 Promise、以固定 sleep 代替就绪条件、吞掉异常后报告成功。

- 在调用链传递取消信号与有界超时；区别取消、明确失败和“结果未知”。超时不能推导外部操作已终止。
- 错误通过稳定错误码与可行动说明传递；包装时保留去敏后的原因。日志关联 task/attempt/operationId 与实际版本，按事件必要性记录；不写密钥、完整鉴权头或默认转储用户内容。
- 插件 dispose、失去写权或关闭入口后，旧回调不得继续提交业务状态；测试应覆盖仍在途的异步完成，而不只检查清理函数被调用。

**〔约束，DEV-07〕** 真实上游 API 鉴权、额度、QPS、连接或流中断错误首次出现时，执行模块必须按 ORG-13 与技术架构 SOLO-F09 停止受影响的后续动作、保留事实并通知用户；不得自动重试、换路由、归档、删除或批量取消。恢复须用户明确指令。评审必须检查实际 SDK、中间件与模型适配器的重试行为，不能只检查业务层 catch。

纯离线测试主动注入的模拟错误属于用例输入：断言停线、通知与禁止重试后可继续下一条用例；这不构成真实上游事故。测试中发生任何真实上游错误仍按本条处理。故障后的自动探测、重新查询或生成请求不能借“恢复检查”绕过停线边界。

## 5. 状态、并发与外部副作用

**〔约束，DEV-08〕** 修改业务写路径的开发者必须列清实际提交点、事实归属及原子边界，由 core 执行身份、准入、占用与写权检查。涉及跨进程写入时，检查和发布必须满足技术架构 SOLO-FENCE-01 对真实存储身份与 fence 的要求，验收关联 ORG-06；同实例 `already-open`、进程内锁或单次原子 rename 均不足以证明通过。

- 并发更新以权威状态/revision 判定；单条记录原子更新不能外推成跨表事务。涉及多条事实时显式设计部分成功、恢复和幂等行为，避免虚构事务保证。
- 命令的 `operationId` 或等价稳定键须贯穿提交、结果和恢复；重复请求返回原操作或可判定结果，不能重复执行不可逆副作用。客户端按钮禁用只能改善交互，服务仍须防重复。
- schema 变化必须说明旧数据读取、版本识别、迁移边界和失败恢复。未经目标版本读回验证，不承诺兼容回退；破坏性迁移前须有已核验的一致恢复点。
- 数据根、profile 与恢复按 ARCH-D03/04、SOLO-DATA-01–04 执行；程序使用注入的路径与公开 home 解析能力，拒绝越界/别名绕过，不依赖个人机器目录。切 profile 只改变装配的事实不能当作数据恢复证据。

**〔约束，DEV-09〕** 外部制作操作提交前持久化操作意图/稳定键，获得 `jobId` 后由 core 保存原始关联。断连或超时且结果未知时保留待核对状态；在停线规则允许且获得恢复授权后核对原操作，禁止盲目提交新任务。外部服务缺少幂等或查询能力时须显式保留未知结果并交给用户裁定，不能假定失败重做。

素材保存必须验证长期位置、真实字节与准确版本，再发布“已保存”结果；错误不得把临时 URL、只存在的空文件或未下载的 job 结果当长期资产。恢复不能承诺撤销已经发生的外部副作用。详细机制与验收沿用技术架构第 7、10、11 章。

## 6. Web、输入与权限

**〔约束，DEV-10〕** Web 作者必须让界面从 Host 权威投影重建；组件只拥有选择、展开、输入等交互状态。客户端缓存及待提交输入都不是业务权威；提交时由 Host 重新校验，不以本地缓存的“已完成/已批准”推进业务。

- 明确显示加载、空结果、失败、等待用户回答与已提交的区别；异步旧响应不得覆盖较新的对象/版本。提交按钮先表示处理中，收到权威结果后才显示保存或接受成功。
- 接受/退回必须绑定准确作品版本；可回答入口与待回答状态一起可见。权限禁止由服务拒绝并说明，不能只隐藏按钮。
- 用户路径使用清楚的产品语言；日志、存储身份和插件名仅在有助于诊断的入口展示。交互元素使用语义化控件、可见标签与键盘焦点，用户可通过键盘完成本切片关键操作。
- 对模型、文档、外部服务及文件中的文本按数据处理。展示时转义；需要富文本时使用允许清单；禁止未处理的 HTML 或把文本拼接成 shell 命令。
- 文件和产物访问在服务侧检查身份、归属与允许根，测试目录穿越、路径别名及无权引用。浏览器包和提交仓库不得包含密钥、用户会话或生产数据副本。

## 7. 测试与证据分层

**〔约束，DEV-11〕** 开发者按受影响行为选择下表检查；评审者核对证据是否真正覆盖该边界。可测试的缺陷先复现目标失败，修最小因果路径后复跑；新行为先给失败用例再实现。沿用匹配当前基线的有效失败证据，环境搭建失败不充当功能失败证据。

| 变更 | 至少覆盖的边界 | 证据限制 |
| --- | --- | --- |
| 纯领域规则/状态转换 | 正常结果、非法输入/权限或非法状态、相关重复与冲突情况 | 纯函数通过不证明 Host 接线正确 |
| 公开接口/适配/依赖升级 | 输入输出与错误契约，真实公开入口，打包后安装与 Host/client 依赖边界 | mock 只证明与 mock 约定一致 |
| 持久化/schema/恢复 | 合成旧数据、失败中断、同一安装组合写入→停止→冷启动→读回 | 清空数据后启动不算恢复；参考 SOLO-ACC-05/06 |
| 写权/路径隔离 | 两个真实 Host、别名根、失权旧句柄、检查与发布间竞争、异常退出；分别核对根路由 | 按 SOLO-ACC-09/10 场景细化 ORG-06；同进程测试不可替代 |
| 上游失败/异步任务 | 离线注入错误，断言首错停线、通知、无自动重试；原操作结果未知与显式恢复 | 参照 SOLO-ACC-07/08；真实调用资格另行验证 |
| Web 用户路径 | 真实界面上的操作、加载/失败/等待、版本绑定与权限拒绝；必要时补 DOM 回归 | 组件测试或截图不证明产品成果可接受 |
| 装配/交付组合 | 精确工件、完整配置层与锁，startup 冷启动和目标 client 组合 | dump 仅证明配置；参考 SOLO-ACC-01、ARCH-D04/07 |
| 纯文档/机械编辑 | 内容、引用、格式与实际差异 | 不要求无关全套运行测试，不写只对比措辞的测试 |

测试使用任务专属临时目录与合成数据；跨 Host 验证使用与生产隔离的测试 home 和实际目标文件系统。独占用例让两个 Host 指向同一规范化临时业务根以产生真实竞争；隔离用例分别使用不同根并核对实际路由。在授权范围内控制资源并于结束时释放。断言用户可观察行为和数据不变量，不镜像内部函数调用次数；超时有界，不依赖公网、墙钟运气或真实密钥。

架构中标为〔建议〕的验收编排是测试设计依据，本文不把其全部细节一并确认；实现切片须按已定需求补齐实际通过标准。检查不通过时保留失败证据，修复或明确未交付的边界；不能通过删用例、放宽要求、把故障改成成功提示来过关。没有变化或新疑点时复用仍有效的证据，避免重复全量检查。

## 8. 协作、复用与交付

**〔约束，DEV-12〕** 每个可写文件/共享状态只有一个当前写者；并行分工先明确目录、接口和消费关系。存在冲突风险才使用隔离 worktree；无既有约定时放在项目根 `.worktrees/<task>/`，新分支默认 `codex/<task>`。隔离区与输出须排除在递归复制、运行发现和打包之外；不更改其他人的未提交内容。

- 同一工作树的 Git index 和集成操作由一个集成者串行负责；提交前检查实际 diff 与暂存区，只包含本候选已核实的范围。
- 复用代码保留许可证与来源，在实际承接模块或包的说明中记录版本及必要改造；按能力选择合格实现，避免整体复制旧插件再改名。新增依赖须解决当前具体问题，声明运行依赖与开发依赖，并检查许可、公开 API、平台和工件兼容。
- 完成、失败或取消时处理任务专属进程与临时工作区；只清理本任务资源。未交付内容或仍有消费者的 worktree 保留路径、负责人、具体原因与释放条件，记录在原生任务/交接中。不得为了干净状态删除用户文件或未交付改动。

**〔约束，DEV-13〕** 作者交付候选时应提供：对应需求与前后行为、改动范围、代码/工件标识、实际检查命令和结果、剩余限制、适用时的数据兼容与恢复路径。阻断正确性、安全或已承诺验收的问题必须处理后才能标记该边界通过。持久写权、恢复、权限与真实执行接线变化须有有界独立复核，评审者直接核实结论所依赖的源码与实际证据。

构建、打包、安装、实际调用、重启恢复、目标集成和用户最终验收分别记录；一层证据不得替代另一层。验证基线变化后更新受影响证据。提交信息使用 `type(scope): 行为摘要`（如 `fix(core): 拒绝失权后的组织写入`），说明问题、最终行为与关键验证；遵守项目已有的提交/集成/发布授权，不把本地候选说成已部署。

### 8.1 本仓库的 Issue、执行任务与 PR

**〔约束，DEV-15〕** 承接用户 2026-09-16 选择 Issue 为工作意图入口，并授权完成 PR 门禁及首个 PR 的要求。队长与开发者开展本仓库已授权工作时，按下表关联工作与成果；本节不规定未来 SoloIPs 公司、部门的 GitHub 接入实现。

| 对象 | 维护的事实 | 维护者与关联方式 |
| --- | --- | --- |
| GitHub Issue | 工作来源、需求或提案的状态、验收条件、讨论与交付结论 | 队长、开发者或 QA 可创建；队长可以整理用户已授权需求，新增业务建议仍标为提案。登记不等于用户确认，用户无需亲自录入 Issue |
| DSH Task | 本次执行的分配/领取、依赖及实际启用契约支持的执行状态 | DSH 承接时，由其任务权威维护；Task 引用 Issue URL，Issue 记录真实 Team/Task 标识及结果入口，一个 Issue 可以拆成多个 Task。attempt 与业务审核按 SOLO-TEAM-03 适配验证，不声称官方原生已提供这些能力 |
| GitHub PR / CI | 某个候选的文件差异、提交、检查、审查与合并结果 | 作者关联 Issue，评审者审查准确提交，集成者核对检查和验收范围；一个 Issue 可以关联多个 PR |
| 已提交文档 | 稳定需求、设计与规范 | 修改相应既有权威并关联 Issue/PR；执行进度与当次检查回执留在工作项中 |

**执行接续。** 队长先明确验收和实际执行方式，再分配工作。DSH 承接时，成员通过原生分配/领取入口执行；Issue 的负责人表示对交付负责的人，Task 的执行者表示具体执行人，两者可以不同，不能把 GitHub 指派当成原生任务已领取。自动桥接未配置时，由队长维护关联及关键结果，避免两边独立改写同一执行状态。用户交由当前会话直接完成的有界工作，可以在 Issue/PR 记录执行者、候选和证据，并明确未使用 DSH Task；不得补造 Task ID，也不得把该次交付说成 DSH 集成验收。

**审查与合并。** 作者从集成分支建立短分支，提交前完成适用检查；PR 使用仓库模板，列明来源 Issue、变更与 DEV-13 证据。评审者在合并前独立检查候选，发现阻断问题先修复；新提交出现后复核受影响结论。集成者确认候选仍为已审查提交、必需检查通过、目标分支满足最新基线要求，才通过 PR 合并，不使用管理员绕过或直接推送 `main`。

**完成与关闭。** PR 只交付 Issue 的一部分时使用 `Related #NN`，保持 Issue 未完成；只有该 PR 足以满足全部验收条件时才使用 `Fixes #NN`。验收还需合并后验证时，先合并并完成验证，再由负责人记录结果、以完成原因关闭 Issue。DSH Task 的审核按原生流程记录，合并不能代替该审核；误报、取消或不采纳必须记录相应原因，不能写成已完成交付。

**门禁与证据。** 集成策略在[项目绑定](project-binding.yaml)维护：必须 PR、必须通过 `verify`、基线保持最新、管理员受约束，禁止强推与删除。单账号协作允许 GitHub 必需批准数为 0，但仍须保留合并前的独立复核记录；智能体复核与独立 GitHub 账号的批准分别报告。实际保护配置、PR 触发的 CI 与合并结果分别从 GitHub 核实，`push` CI 通过不证明 PR 流程通过。验证使用任务分支和真实小改动，不向 `main` 推探针，不为撤回探针临时放开强推。

## 9. 首个实现切片的使用顺序

**〔约束，DEV-14〕** 获授权的 S0 开发者按以下顺序让规范变成实际可执行约定；不以补齐全部远期能力为开工前提：

1. 绑定需求/验收、真实 DSH 安装候选及测试数据根，确认现有工作区与写者。
2. 建立 DEV-02 所需的最小 workspace、锁与检查入口；只加入当前需要的包和依赖。
3. 给当前行为一个失败证据，沿公开入口完成最小调用路径；保持业务写入在合格门禁之内。
4. 运行适用静态检查、行为测试与安装/Host 验证，按 DEV-13 复核并交付候选。
5. 在已获授权的交付目标验证实际结果；其余未获授权的服务或产品动作留在明确边界外。

**前置条件与交付物分开**：开始切片前明确当前动作授权、需求/最小验收、写入范围及所需兼容证据。DEV-02 的 workspace、锁和可执行配置由步骤 2 交付；缺少这些文件不构成“先做完实现才准开工”的条件。原生任务登记按 ARCH-D06 和项目绑定执行；尚未配置的能力不能声称已就绪。操作现有服务或真实数据前必须补齐[环境交接](../operations/environment-handoff.md)中该动作的身份、数据根、在途操作与恢复条件；不要求离线目录设计先完成生产恢复演练。公司写入启用仍须满足 ARCH-D07/ORG-06。
