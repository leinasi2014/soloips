# SoloIPs 文档格式规范

| 阅读契约 | 内容 |
| --- | --- |
| 身份 | `SOLOIP-DOC-001`；SoloIPs 仓库全部文档的格式与标注唯一正文 |
| 目的 | 让智能体无需人类口头解释即可定位规则、适用条件、证据状态与待决项，降低跨会话与跨成员交接的信息损失 |
| 范围 | SoloIPs 仓库内全部 Markdown 文档：需求、架构、决策、交接、任务说明、README、索引 |
| 决策状态 | 〔需求〕用户 2026-09-15 确认：所有文档面向智能体清晰可读；本项目以智能体团队开发为主 |
| 依据 | `AGILE_SKILL_ROOT/references/agent-readable-documentation.md`（通用方法，跨项目）；技能名与本机位置按[环境交接 ENV-02](../operations/environment-handoff.md)解析，本文是 SoloIPs 的落地正文 |
| 实现证据 | 本文是规范文本，不含产品运行证据；文本本身按本文格式书写，可作样例 |
| 变更权 | 用户；修订只更正本文唯一正文，不新建同题副本或第二份格式说明 |

## 0. 阅读顺序

目的与状态 → 术语与边界 → 需求 → 设计与数据归属 → 失败与恢复 → 验收场景 → 待决事项。

小文档只保留适用子集；不要求每份文档齐备全部小节。细节放在支撑它的决策旁边，读者进入任一小节应能恢复该节的范围与适用规则，无需加载无关历史。

## 1. 阅读契约

每份实质性文档开头给一个紧凑元数据块（推荐上表形式），至少包含：文档身份、目的、范围、决策状态、证据范围、依据、变更权。负责人与路径复用 `docs/governance/document-registry.yaml`，不在每个文件里重复抄写。

短文档用一句话表达同一契约即可。YAML front-matter 可选；**SoloIPs 统一采用 Markdown 表**，便于模型与脚本一致解析。

## 2. 三类标注必须分开（本规范核心）

三个维度正交，不得互相推断：

| 维度 | 取值 | 判定规则 |
| --- | --- | --- |
| 决策 | 〔需求〕已确认 · 〔约束〕既有约束 · 〔建议〕设计建议 · 〔待决〕未决 · 〔已取代〕已被替换 | 确认必须有来源（用户或获授权主体）。**智能体之间达成一致不构成确认。** 不得从早期阶段推断后期阶段 |
| 证据 | 〔源码事实〕带来源与基线的观察 · 〔推断〕含假设 · 〔未验证〕未知或证据缺口 | 关键词搜索无结果不等于证明不存在。事实须绑定来源、版本或日期、已证边界 |
| 交付 | 〔提案〕· 〔已实现〕在指定候选 · 〔已验证〕在指名边界 · 〔已集成〕在指名目标 | 不得从"已实现"推断"已验证"，也不得从"已验证"推断"已集成" |

**复合陈述拆分**：一条陈述只要有一部分仍属建议，就不得整体标为〔需求〕，必须拆成独立条目分别标注。

## 3. 稳定 ID

需要跨引用的需求、决策、验收场景必须分配稳定 ID，形如 `SOLO-01`、`DEPT-01`、`ORG-03`、`AVATAR-64-01`：

- 重写保留原 ID；含义改变时标出取代关系（`〔已取代〕→ 新 ID`）。
- 不是每段都需要 ID；只给需要被引用的规则与场景。
- 引用时写 ID，不写"如前所述"。

## 4. 可执行规则的写法

行为类规则须显式给出：**actor**（谁）· **trigger/precondition**（何时、何前提）· **action**（必须/应当/可以做什么）· **scope**（范围）· **outcome**（可观察结果）。涉及正确性时补：**authority**（授权来源）· **failure/recovery**（失败与恢复）· **verification**（验证边界）。

动词用「必须 / 应当 / 可以」或 MUST/SHOULD/MAY，全文一致。**出现在〔建议〕内的"必须"只描述该建议成立所需条件，不是已生效命令。**

业务需求与实现备选分开陈述：需要取舍时记录推荐项、理由、未决证据与决策责任人。不要因为团队尚未调研，就把存储选型之类的问题抛给用户。

## 5. 反面声明

存在具体歧义时，明确写出"这条不蕴含什么"。SoloIPs 常用区分：

- 持有不等于可访问。
- 安装启用不等于实际被调用。
- 文件存在不等于内容有效。
- 模型判断不等于宿主授权。
- 一个环境通过不等于普遍兼容。
- 任务完成不等于已发布或已验证市场效果。

只保留与本档真正相关的区分，不堆砌。

## 6. 证据绑定

- 绑定 **来源 + 相关版本或日期 + 已证边界**。
- 项目内文件用仓库相对链接；外部来源用直链。
- 可复用文档使用符号环境名；机器本地绝对路径和瞬时进程细节写入运维交接的本机记录，不进正文。密钥、鉴权头与用户会话正文不得写入规范或交接证据。

## 7. 单一权威与合并

- 更新**最小**的既有权威章节，不新建同题 PRD / ADR / 摘要 / 状态台账。
- 投影的 `sourceAuthority` 列明直接依赖的登记文档；维护者在来源变化的同一候选中核对相关投影与引用。没有自动刷新工具时执行人工核对，不把登记字段当作已运行能力。
- 评审修正直接合进正文；读者不应靠回翻聊天记录才发现某条规则已被撤回。
- 保留未决项并显式标注；取代旧决定时引用被取代者。
- 动态状态（谁在做、卡在哪、哪个版本可用）留在原生任务与发布系统，不写进已提交文档。

## 8. 工具选择

- 检索用标题；并列比较用表格；代码块标注语言；有实质歧义时才给简短样例。
- 不依赖颜色、图片或图表作为规则的唯一载体。
- 保留机读 schema 与可执行契约作为独立权威并链接，不手工复制其内容。

## 9. 验证

- 检查陌生读者能否识别：预期结果、现行规则、剩余决策、实际可用证据。
- 逐条追踪实质需求 → 规则 → 验收样例；检查冲突条件、遗漏的失败转换、混用标签。
- 检查本地链接、稳定 ID 与改动内容，然后运行项目自有文档检查。
- 不为散文新建只数标题或比对措辞的验证器。
- 需要时做有界独立复核；只复核改动过的结论，不重审未变历史。
- 文本复核与场景走查**不等于**已执行的产品测试；如实报告实际检查了什么。

## 10. 与既有文档的关系

本规范适用于**新增或实质性修订**的、承载决策的章节。不要求为满足格式而整体重排历史文档。

`docs/refactoring/` 系列（若引入）使用的 〔需求〕〔约束〕〔建议〕〔待决〕〔源码事实〕〔推断〕〔未验证〕 标签与本规范一致，可直接沿用；本文只补充交付维度标签与阅读契约的固定形式。
