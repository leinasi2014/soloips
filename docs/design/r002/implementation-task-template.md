## 0. 这份模板怎么用

1. **不要在本文件里另写流程规则。** 流程规则的唯一正文是 [Skill §8](../../../.agents/skills/team-delivery-leadership/references/soloips-development.md)。本模板只做两件事：**把 Skill §8 的要求变成可填写的格子**，以及**给出填写示例**。

## 1. 闸门与责任人（引用 Skill §8.2，含 Lead R1–R5 裁定）

> 规则正文见 [Skill §8.2](../../../.agents/skills/team-delivery-leadership/references/soloips-development.md)。下表是**本轮已裁定**的落地形态。

| 闸门 | 检查什么 | 谁放行 | 裁定依据 |
| --- | --- | --- | --- |
| **G1 架构评审** | 前后架构是否**实测**、爆炸半径是否列全、契约是否完整、前瞻必答是否答出**具体功能名**、**登记一致性**（新增正文已登记 / 登记路径存在 / `sourceAuthority` 无悬空）、**§7.2 未冻结面是否被误用** | **任一非作者成员**（规则原文是「非作者」，不是「必须 QA」）：代码类 → 另一名开发；文档类 → 文档复核者 | R3 |
| **G2 机械门禁** | `format:check` / `lint` / `typecheck` / `test` / `build` + **组合断言** + **脱敏语义核查** + **可执行性核查** | 自动，**以具体观察为准** | R1/R2、Skill 8.2/8.3/8.4 |
| **G3 提交复核** | **收窄到三项只属于它**：① 准确提交与 G1 通过的契约**逐项一致**；② **失败用例确实先红过**；③ DEV-13 证据格式齐备 | 非作者 | R3 |
| **G4 真实验收** | SOLO-ACC 场景，**版本级**执行 | `verifier`（**但不得为该产物的作者**，R5） | R1、R5 |

### 1.1 五条通用判据（**不得违反**）

1. **不得用「退出码 0」或「CI 绿」作为任何闸门的通过判据。** 每道闸门须给**具体观察**——dump 的哪一行、命令的哪个退出码、请求计数的哪个值（Skill §8.2；技术架构 §11.1 / SOLO-F06）。
2. **「独立」是不可合并的常量，「深度」是可调变量**（R2）。深度分级 L1/L2/L3 见 Skill §8.2。
3. **同一人执行 G1/G3/G4 时，其独立性弱于分派三人，须原文记录该限制**（R3）。
4. **门禁必须自证确实运行了**：每个新增门禁交付时**必须附一条「注入已知失败 → 断言失败」的证据**（Skill §8.4）。**只验正向通过不够——恒返回 0 的门禁也会「通过」。**
5. **〔约束〕作者不得作为其自身产物的任何闸门复核者（G1/G3/G4 通用，不限于 G1）**（R5）。**依据**：[Skill §8.11](../../../.agents/skills/team-delivery-leadership/references/soloips-development.md) 是该规则的正文；Skill §8.2 的 G1/G3 行只写「非作者」，**未禁止「作者复核自己的产物」**——该缺口的具体实例是：`acceptance-plan.md` 的作者若同时做该文档的 G4 复核，即构成自审，与 Skill §8.11 冲突。

   **本条的依据说明**（`integrator` 反对意见原文要点，R5 采纳理由）：

   > **流程的真实安全来自「多名智能体互相不同意」，不是来自闸门本身。** 本轮实证：B-1 由 `verifier` 发现而 `doc-reviewer` 首轮漏报并自我更正；B-2 断链由 `doc-reviewer` 发现而执行者未测到；`integrator` 的两项阻断回归**均由他人抓出**。→ **缩减复核者数量会断崖式降低发现率**，而 `project-binding.yaml` 的 `requiredApprovingReviewCount: 0` 会让这种缩减**看起来像已满足要求**。**因此「作者不得自审」不是形式条款，而是保留「互相不同意」这一发现机制的下限。**

   **本条与第 3 条的关系**：第 3 条处理「同一人兼任多道闸门」的**独立性衰减**（须原文记录限制，仍允许兼任）；**第 5 条处理「作者复核自己产物」的禁止**（无条件禁止，不接受记录替代）。两者**不重叠、不互相豁免**。

### 1.2 G4 分层（R1）

| 层 | 含义 | 何时可跑 |
| --- | --- | --- |
| **G4-M 机制层** | 已安装 DSH 工件 + **任务自建临时根**，验证宿主机制（dump 组合、持久化、跨进程独占、冷启动读回） | **现在就能跑**，不需要产品实例 |
| **G4-P 产品层** | SoloIPs 业务出口（公司/部门/员工/准入/派工/停线通知） | 等实现授权（A3）+ 实例 |

**G4 按「验收场景就绪度」触发，不按功能触发**（Skill §8.3）。多数 SOLO-ACC 场景是**跨功能**的——`SOLO-ACC-04` 需公司/部门/员工/入职齐备，`SOLO-ACC-05` 需公司+部门+员工+任务+作品版本齐备。**硬要求每功能 G4 会导致「为凑验收而伪造前置数据」，比不做更糟。**

## 4. 授权链与暂停（引用 Skill §8.7）

**三段式**：**用户批准需求 → 队长批准调度 → 协调者派工**。

- 协调者是**调度者**：派工、盯进度、汇总、上报、把关闸门、维护 Issue/PR 关联；**不认领交付物**。
- **必须停下请示用户**：[`AGENTS.md` §2](../../../AGENTS.md) 的 **8 种暂停条件**：① 超出任务目标 ② 超出允许目录 ③ 修改组织规则 ④ 修改权限系统 ⑤ 修改身份体系 ⑥ 不可逆破坏操作 ⑦ 对外发布（push / PR / 上线）⑧ 需要新的业务决策。
- **临时工**（编制已满时）：**任务负责人自己派**（用 `workflow`），不需经 Lead 或 coordinator。规则见 Skill §8.6 与 `teammate-and-temporary-worker-policy.md`。
