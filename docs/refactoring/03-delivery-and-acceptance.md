# 重构交付顺序与验收

| 阅读契约 | 内容 |
|---|---|
| 身份 | `refactor-delivery-acceptance` |
| 依据 | [公司合同](02-company-contract.md)、[部门与资料室](01-departments.md)、[头像规范](04-avatar-64.md)及用户最新要求 |
| 状态 | 重构开发与验收基线；实际完成情况以任务、提交和运行证据为准 |

公司重构的交付顺序：先咨询与三模型只读反驳审查，由统筹解决阻塞，再按以下可独立使用的纵向批次执行；不先建立全部模块空壳。

| 阶段 | 可使用出口 | 本阶段必要边界 |
|---|---|---|
| 第一片：一个部门的完整工作闭环 | 建部门、任命管理员、招募/完整入职、真实领取/交付/审核、必要 UI、重启恢复 | 用户 Host/RPC 入口、个人文档持久版本/装配、所有正式准入、跨 Team/多 Session 单员工占用及旧入口无绕过、实际单 writer、撤权与 claim 一致性、operationId 恢复出口；只新建员工，验证后即可发布试用 |
| 第二片：两个部门协作 | 部门/员工入口、能力发现、定向咨询、正式交接、资料室成果引用与审查 | 跨部门授权、去重/预算/暂停、无双派工和越权知识；这是基础版必需，不能整体推到远期 |
| 第三片：人员变化 | 正常/紧急更换管理员、调岗、冷处理/恢复、新任职续接与恢复；旧 Team 迁移只在另有用户需求时启动 | 第一片就预留并验证控制风险，不拖到本片才发现不能接管；彻底删除按未决权利/能力限制明确标注 |
| 第四片：成长及知识治理完善 | 增量整理、个人职业 Skills→获准通用版本→实际加载→纠错撤回 | 第一片已有个人文件/初始化/正常自我修正，复用已有记忆与 Skills；更广自动教学、性能研究为后续扩展 |

每片一条 Feature Pipeline，独立验收后经现有 Git PR/发布流程进入可用版本；能力相关缺陷仍回原 Issue 管理。整体基本版需覆盖能力架构 ORG-A01–08 的对应出口，未验部分明确列限制，不能把第一片叫全部完成。源码/文档、工程测试、真实模型、浏览器、重启、实际安装分别报告。

## 每片交付必须核对

- 任务携带重构需求 ID、实际工作目录、负责人和验收场景；旧代码与旧测试只能作为侦察证据。
- 需求逐项对应生产入口和反例；ORG-03 必需项缺失时，派单、自领、调度和重试均拒绝正式工作，并提供修复入口。字符串标记、文件存在或模型自报不能代替有效头像、版本读回、实际请求装配及能力验证。
- 独立复核同一个候选；集成清单列出该片所需实现及依赖，核对构建包、配置和安装运行版本确实携带它们。启动新服务或创建新团队不能代替此检查。
- 同一安装候选通过真实模型工作闭环、浏览器及必要重启验收后，才报告对应能力完成。原有工程命令可作为检查工具参考，其 PASS 不自动满足重构需求。
- 需要恢复时先保护已提交数据和在途事实；新重构不为保留旧执行器追加兼容开发。
- 上游 API 错误按[公司合同 ORG-13](02-company-contract.md)立即停止受影响执行并通知用户，禁止先自动重试、自动换模型或归档团队；恢复执行与团队处置遵循用户明确授权。以 ORG-A09 验证，不能把预防错误归档的补丁当作完整停线和通知交付。

## 后续切片：通知方式配置与外部通道

用户已确认预留短信、邮箱通知和插件内通知方式选择，契约集中在[公司合同 ORG-13](02-company-contract.md)。本轮只记录接口占位；插件选择/配置读回、短信/邮箱通道实现及真实通知验收以后作为同一切片交付，不在当前修复中接入供应商或发送测试短信/邮件。

空接口返回 `not_implemented`，未配置返回 `not_configured`，两者都不算发送成功；站内错误通知不依赖外部通道就绪。后续交付按 ORG-A10 核对选择生效、接收目标保护、错误合并、失败可见及真实发送/送达边界。上游错误立即停止和保留团队/任务事实属于当前执行安全要求，不能随外部通道一并延期。

## 重新组队与成果接手

**用户确认要求（2026-09-15）：** 重新组队前冻结旧队执行，保留工作记录及完成/半成品成果；用户明确要求删除旧团队时，在核对保存范围后走正式清退入口。新队使用新 Team、Captain、成员及任务身份，旧记录作为可追溯交接资料，不自动恢复旧 attempt。

- 先对照本目录需求 ID，区分可安装成果、候选代码、已知缺陷和未实现项；任务 accepted、文档声称通过或启动新服务均不能替代安装验收。
- 当前目标服务为用户指定的 55120；先核对实际 Profile 安装并启用 RLM 插件，确认宿主和 Web 插件配置生效。新队主会话、队长及成员统一使用官方 `ptc` Agent 预设（PTC 模式），核验每个实际会话的预设与工具呈现；不能把安装 RLM 等同于选中 PTC。安装包存在不等于工具可调用。
- 将通过对应检查的已完成成果整合到目标服务；类型不匹配、缺少真实入口或尚有已确认缺陷的候选保留并交给新队修复，不冒充完整交付。
- 新任务必须指向剩余需求、旧候选来源、基线及代表性验收；GLM 仅文档，开发由 Qwen/DeepSeek 承担。自动推进在重组完成且获准恢复前保持暂停。
